# strata.spec

## 概述

为一项变更产出目标规格：完成时什么必须成立，写成每条标准都可以被验证的形式，以及它与系统目前的行为有何不同。

## 适用场景

收到变更请求但不存在目标规格；规划文档缺少验收标准；用户询问规划与当前行为是否一致。纯重构且行为不变时不适用。回答规划与行为是否一致是只读；编写或修订规格时升为单会话（DEC-2026-11-01-18）。

## 流程

1. 阅读规划来源以及该变更涉及的现状形态文档。证据：已读文档列表。
2. 写出目标、范围（范围内与范围外）、验收标准（每条附上将证明它的证据）、来自适用建议卡片的约束，以及遗留问题并注明由谁回答。证据：规划文档中的相应章节。
3. 列出目标与现状形态之间的差异，每条一行。证据：差异列表。
4. 标出任何需要新增架构决策的标准；不要在这里做决定。证据：被标出的条目。
5. 对本次会话新写或修改的每份规划文档，以实现评审收尾。`implementation.status` 按第1、3步确认的结果填写（implemented、partial、diverged、not-implemented 或 superseded，不留作 unreviewed），`reviewed` 填今天的日期，`spec` 填其 covers 拥有实现该规划的代码的 as-built 规格。若没有规格拥有该代码，不要默默留空 `spec`，而是在差异列表中写一行（“没有规格拥有 <路径>”）。覆盖率门禁从变更代码沿 `spec` 回溯到规划；没有 `spec` 的规划对门禁不可见。证据：implementation 块。 评审中发现规划与实现不一致时，留下判定请求（`python3 -m kb divergence add`，关卡的重新核对行用 `kb coverage-gate --divergence-inbox`）并询问人；不要自己选择判定（document-format 的规划编写规则，DEC-2026-10-31-35）。

## 借口与反驳

| 想法 | 反驳 |
|---|---|
| “用户已经在聊天里讲清楚了。” | 聊天不是持久的产物。把它写进规划文档，否则下一个会话就拿不到。 |
| “验收标准可以在实现之后再写。” | 那样它们描述的是做出了什么，而不是想要什么。先写。 |
| “差异列表显而易见。” | 照样要写；收敛关卡读的是它，而不是你的记忆。 |
| “实现评审可以以后再做。” | 以后很少到来：导入的规划大多仍未评审。本次会话触及的规划，趁代码还开着现在就评审。 |

## 警示信号

- 某条标准没有指明证据。
- 规格直接修改了现状形态文档。
- “按讨论的实现”，却没有文档。
- 以未评审状态关闭的规划文档，或既无 `spec` 也无说明原因的差异行的规划文档。

## 验证

- 每条标准都指明了证据。
- 差异列表存在。
- 遗留问题都指明了负责人。
- 每份触及的规划文档都有 implementation 块（status、reviewed、spec 或说明缺少规格的差异行）。
