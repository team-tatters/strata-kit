# strata.planning

## 概述

规划阶段是一道过滤器（DEC-2026-11-01-04）。原始规划里混杂着尚未定下的讨论、代码和规则；如果原样注入，之后的每个读者（检索、Onyx 这类注入工具、同事）读到的都是垃圾。所以不直接总结来源，而是把它拆成事实，一行一条，并给每一行一个去向。只有整理稿——PRD（人能观察到的规则）和 Logical Tech Spec（实现更换后仍然成立的保证）——以及决策记录会被注入和共享；来源和工作表格作为依据保留。**规划文档不写代码，也不写架构**：表、列、类、服务、API 路径、HTTP 状态码、框架和供应商都归入 'code' 去向，作为规格、订单或决策的素材。

## 适用场景

收到外部规划来源；创意笔记（ideation.shape）已经可以变成规划；现有资料包需要检查其对照表。不用于为已整理好的规划编写验收标准（strata.spec），也不用于架构选择（strata.decision）。只阅读来源时，工作模式是只读；写资料包时升为单会话；资料包需要不止一个会话完成时为多会话——每个会话结束时都要交接（DEC-2026-11-01-18）。

## 流程

1. **把来源变成事实清单。** 将来源原封不动地放在 `source/` 下（或标记为 `category: source`）。在 `audit/facts.md` 中一行写一条事实——规则、权限、状态转换、例外、数据、界面、验收标准、决策、假设、依赖、修订历史。列依次为：`# | 来源位置 | 类型 | 内容（一句话，保留来源原意） | 角色（规划 · 规格 · 代码 · 背景 · 重复） | 轴 | 子主题`。轴是规则必须回答的五个问题：identity、time、derivation、expiry、conflict（同一性、时间、派生、失效、冲突）；都不适用时写 `n/a`。证据：事实清单。
2. **树与决策。** 把子主题归组成树的草稿，在写任何正文之前取得本人确认。来源之间的冲突，或与后来决策的冲突，都作为问题提出；约束架构的答案用 strata.decision 记录。证据：已确认的树、问题及其答案。
3. **编写整理稿，并给每一行一个去向。** 在 `audit/coverage.md`（`# | 来源位置 | 去向 | 备注`）中，每条事实恰好获得七个去向之一：`<document> R<n>`、`isolated:<group>`、`defect:<what>`、`code`、`background`、`duplicate:#<n>`、`out of scope:<bundle>`（依次为：已反映在整理稿中、隔离、缺陷、代码、背景、重复、范围外——接收方资料包的对照表中须有同一行）。矛盾和缺漏写入 `audit/defects.md`，并注明整理稿如何处理。PRD 和 Tech Spec 分别标记 `planning_doc: prd` / `tech-spec`。证据：对照表。
4. **复杂度审视。** 当某个功能的策略超出人能记住的量（检查报告 PRD 超过 800 词或 10 条规则、Tech Spec 超过 1,200 词）时，按状态制作策略表，并提出隔离阶段或状态的方案。隔离会改变策略，所以由本人决定；被移走的规则放入 `audit/isolated.md`。证据：方案与决定。
5. **在新的上下文中检查。** 运行 `python3 -m kb planning check <资料包>`：没有去向的行、重复计数、接收方没有的移交、没有轴的规则行、上限、整理稿中的代码表述（只查整理稿——来源和 audit 里写什么都可以）。修正后重新运行。然后把资料包发给 strata.review，只做检查；编写资料包的上下文对它会过于宽容。证据：检查输出和评审回复。
6. **影响。** 运行 `python3 -m kb planning impact <包>`。它从整理稿 frontmatter 的主题节点出发写出 `audit/impact.md`(生成文件,依据层):这些节点的规格、规格负责的代码、依赖这些代码的一层代码及其测试(要看更深用 `--depth`)、这些节点的决策,以及同一节点的其他规划。向人展示摘要行和冲突之处 — 规划与之相悖的现行决策、同一节点的其他规划。是否修改规格或替代决策由人决定。没有节点时,询问规划属于哪个主题节点。证据:摘要行。
7. **下一步。** `python3 -m kb skills next strata.planning`：写验收标准用 strata.spec，或 strata.decision，或什么都不做。**决策捷径：** 如果来源只是一次决策的议程，就跳过整理稿，从事实清单直接进入 strata.spec 或 strata.decision。

## 注入边界

被注入和共享的：整理稿和决策。只作为依据的：`source/`、`audit/`，以及标记为 `category: source` 或 `audit` 的任何文档。边界同时按路径和按分类守住（DEC-2026-11-01-05）：知识检索会跳过依据；`python3 -m kb planning boundary` 输出 GitHub 连接器的排除路径和 share.yaml 的 `never` 行；`--list` 输出注入工具可以读取的整理稿。Notion 在 kit 之外：把放整理稿的页面和放来源的页面分开，让连接器指向整理稿一侧。

## 借口与反驳

| 想法 | 反驳 |
|---|---|
| “来源很短，总结一下就够了。” | 总结会悄悄决定丢掉什么。事实清单则把每一处丢弃都显示为带去向的一行。 |
| “写上表名，规则更清楚。” | 这会把规划绑定到一种实现上，并泄漏进注入内容。把它移到 'code' 行。 |
| “我写的，我自己就能检查。” | 编写时的上下文是宽容的。到新的上下文中检查。 |
| “冲突很明显，选较新的来源就行。” | 那是一个策略选择。把它记为缺陷并提问。 |

## 警示信号

- 本人确认树之前就写好的整理稿。
- 行数少于来源中规则数的事实清单。
- 没有去向的对照表行，或被计数两次的同一行。
- 出现表名、类名、API 路径或供应商名称的整理稿。
- 被就地修改的来源。

## 验证

- `kb planning check` 没有报告缺失去向、重复计数、断开的移交或代码表述。
- 树、隔离和缺陷处理都写明了本人的答复。
- 已在新的上下文中对资料包做过评审。
- 来源原封不动地位于 `source/` 下。
