# Skills

> This page is generated from the sources — do not edit it by hand.

Procedures the agent follows. Every skill ends with evidence requirements.

| Skill | What it does |
|---|---|
| `design.brief` (pack) | This is the person's design stage. Whatever is designed — a document, a physical object, an image, a post, a screen — the work starts from a brief: what it is for, who sees it, in what medium, under which constraints, with which references, and what must be true for it to be done. The brief is the person's; the agent asks and writes down, it does not decide taste. A design leans on the person's taste and on the techniques that express it (a glass surface, a raised soft shadow, a stack of borders and shades); the brief names the ones this work uses. |
| `design.taste` (pack) | Taste is a record of judgements, not a style the agent picks. This skill keeps that record for one project or one brand — never for a person as a whole, because taste is judged in the context the work sits in. The taste note has four sections: taste (lines the person promoted), signals (reactions and picks), inferences (what the agent guessed, marked), rejections (what the person turned down and why). A tag that turns up in three different briefs becomes a promotion candidate; the person decides. The expression note writes how the taste looks: primitives (colour, blur, opacity, spacing, radius, type) once, and each technique as a readable paragraph with a YAML block of layers and relations — lighten and darken in OKLCH lightness, opacity, WCAG contrast — that `kb taste expression` computes. |
| `ideation.shape` (pack) | An idea is useful long before it is finished. This skill helps the person organise an idea until it can be used — in planning, a specification, a decision or a retrospective — without making the idea for them. Each idea is one note with five facets (origin, problem, method, outcome, meaning). Empty facets are allowed; they are the next questions. The agent estimates how many conditions and orders the idea still needs and asks the person to confirm it; the confirmed number is the idea's weight, and the weights of all open ideas are the load of thought the person is carrying. Ideas may grow without limit; an idea left without growth for more than 30 days is offered for archiving, never deleted. |
| `strata.build-task` | Executes one task: reads the specification the task carries, changes only the named files within one layer, runs the verification command, and reports completion with evidence and per-constraint compliance. |
| `strata.decision` | Records an architecture decision as a durable record with the decision writer, in the same session it was made, and extracts a recommendation card candidate when the decision generalizes beyond this project. |
| `strata.distill` | Moves what was learned, not what was written, from the work vault into the personal core: a candidate record on the work side, and a re-written pattern or guide on the personal side that stands without the original context. |
| `strata.handoff` | Writes the handoff that lets the next session continue without this conversation: what was done with evidence, what is pending and why, which decisions were recorded, what to watch, and what to distil into the personal core. Then records, verifies and publishes as three separate steps. |
| `strata.init-wizard` | The wizard assembles a project's guidance from recommendation cards. It interviews only for what code cannot answer, diagnoses the stack against profile detection rules, proposes cards with their evidence, generates adapters once the user approves, and verifies the result. It is also the path for regeneration when the core revision moves. It never writes outside the paths listed in the approved proposal. |
| `strata.kb-update` | Keeps as-built knowledge equal to the code: finds the document that owns each changed path, updates it in place with sources, or records why no change is needed, then regenerates the generated views. |
| `strata.order` | Turns an approved specification into an order and self-contained tasks a worker can execute without the conversation: one layer each, explicit files, constraints from the registry, and the command that proves completion. |
| `strata.planning` | The planning stage is a filter. A raw plan mixes undecided talk, code and rules; if it is injected as it is, every later reader (a search, an injection tool such as Onyx, a teammate) reads garbage. So the source is never summarised straight away. It is split into facts, one per row, and every row gets a destination. Only the refined documents — the PRD (rules a person can observe) and the Logical Tech Spec (guarantees that survive a change of implementation) — and decision records are injected and shared. The source and the work tables stay as evidence. **Planning documents carry no code and no architecture**: tables, columns, classes, services, API paths, HTTP codes, frameworks and vendors go to the 'code' destination and become material for a specification, an order or a decision. |
| `strata.retro` | A retrospective is for the person's understanding, not the agent's efficiency. The agent prepares the material and asks; the person explains in their own words; the agent then points at what the records say and where they are silent. The result is a note the person wrote, plus anything worth carrying into the methodology or the decisions, each handed to the skill that owns it. |
| `strata.review` | Gets an independent check from a fresh context without sharing the whole conversation: a structured packet with the decision, pointer-first evidence and a bounded request, one round trip, and a recorded triage of the answer. |
| `strata.security` | The core gives the operator one note a day: what is new, what is still open, what closed, and which targets nobody is watching. This skill is the person's side of that note. It reads what the daily job wrote, puts the person's judgement back into files (an order, an accepted risk, a threshold, a link), and refreshes the target lists when the person brings new measurements. It does not collect, grade or patch on its own — the daily job collects and grades by the recorded rules, and patching happens only through `patch plan` and `patch run` with a condition that holds. |
| `strata.signal` | The operations stage shows indicators; it does not take over the product's flows. Two kinds feed it: strata's own measurements (kit revision, sessions, verification, handoffs, git) and product-flow indicators a project reads, read only, from flows it already has — a QA ledger, coverage test cases. When one moves the worse way, this skill keeps it as one note with its evidence and hands the choice to the person: it shows what the change could lead to and why, then records what the person picked. |
| `strata.spec` | Produces the desired specification for a change: what must be true when it is done, stated so that each criterion can be verified, and how it differs from what the system does today. |
| `strata.translate` | Fills the missing locales of cards, skill bodies, roles and documents from the canonical text, using the glossary, without changing meaning, identifiers or structure. |
| `strata.verify` | Replaces the impression of completion with evidence. Evidence is written at the moment a test, checker or build runs, and compared at the moment completion is claimed: if a task file changed in between, the evidence is stale and the command runs again. Builds a table of what the owning skill required, what proves each item, and what could not be verified, then states go or no-go. |
| `using-strata` | `using-strata` is the entry point. It does two things and nothing else: it prints where the session is (so the user and the agent share the same facts) and it routes the task to the skill that owns it. It never does the work itself and it never changes; extensions come from the layered registry, not from this file. |
