# strata.planning

## 概要

企画段階はフィルタです(DEC-2026-11-01-04)。企画の原文には、まだ決まっていない話とコードと規則が混ざっています。そのまま注入すると、後で読むすべての読み手(検索、Onyx のような注入ツール、同僚)がゴミを読むことになります。そのため原文をすぐには要約しません。一行に事実一つずつに分け、すべての行に行き先を付けます。注入・共有されるのは整理版 — 人が観察できる規則を書いた PRD と、実装が変わっても保たれる保証を書いた Logical Tech Spec — と決定レコードだけで、原文と作業用の表は根拠として残ります。**企画ドキュメントにはコードもアーキテクチャも書きません。** テーブル、カラム、クラス、サービス、API パス、HTTP コード、フレームワーク、ベンダーは 'code' の行き先に送り、仕様・オーダー・決定の材料にします。

## 使う場面

外部の企画の原典が届いたとき、アイデアノート(ideation.shape)が企画になる準備ができたとき、既存のバンドルの対照表を確認する必要があるとき。すでに整理された企画に受け入れ基準を書く作業(strata.spec)や、アーキテクチャの選択(strata.decision)には使いません。作業モードは原典を読むだけの間は読み取り専用で、バンドルを書くと単一セッションへ上がり、バンドルが一つのセッションに収まらなければ複数セッションになります — セッションが終わるたびにハンドオフします(DEC-2026-11-01-18)。

## 手順

1. **原典を事実リストに。** 原典は手を加えずに `source/` の下に置きます(または `category: source` と印を付けます)。`audit/facts.md` に、規則・権限・状態遷移・例外・データ・画面・受け入れ基準・決定・前提・依存・改訂履歴を一行に事実一つずつ書きます。列はこの順です: `# | 原典の位置 | 種類 | 内容(原典の意味を保った一文) | 役割(企画・仕様・コード・背景・重複) | 軸 | 下位トピック`。軸は規則が答えるべき五つの問い identity、time、derivation、expiry、conflict(同一性、時間、派生、消滅、衝突)で、どれも当てはまらなければ `n/a` と書きます。証拠: 事実リスト。
2. **ツリーと決定。** 下位トピックをまとめてツリーの草案を作り、本文を書く前に本人の確認を得ます。原典同士の食い違いや、後の決定との衝突は質問にします。アーキテクチャを縛る答えは strata.decision で記録します。証拠: 確認されたツリー、質問とその答え。
3. **整理版を書き、すべての行に行き先を付ける。** `audit/coverage.md`(`# | 原典の位置 | 行き先 | 備考`)で、事実ごとに七つの行き先のうちちょうど一つを付けます: `<document> R<n>`、`isolated:<group>`、`defect:<what>`、`code`、`background`、`duplicate:#<n>`、`out of scope:<bundle>`(順に、整理版に反映、隔離、欠陥、コード、背景、重複、範囲外。範囲外は受け取るバンドルの対照表にも同じ行があること)。矛盾と欠落は、整理版がそれをどう扱ったかとともに `audit/defects.md` に書きます。PRD と Tech Spec には `planning_doc: prd` / `tech-spec` を付けます。証拠: 対照表。
4. **複雑さの見直し。** 機能のポリシーが人の覚えられる量を超えたら(チェックが PRD の 800 語または規則 10 個、Tech Spec の 1,200 語の超過を報告したら)、状態ごとのポリシー表を作り、段階や状態を隔離する案を出します。隔離はポリシーを変えるので、決めるのは本人です。移した規則は `audit/isolated.md` に入れます。証拠: 提案と決定。
5. **新しいコンテキストでチェックする。** `python3 -m kb planning check <バンドル>` を実行します: 行き先のない行、二重に数えた行、受け取る側にない引き渡し、軸が空の規則行、上限、整理版の中のコード表現(整理版だけが対象で、原文と audit には何を書いてもかまいません)。直して再実行します。その後、バンドルを strata.review に送り、チェックだけを受けます。バンドルを書いたコンテキストは自分の書いたものに甘くなります。証拠: チェックの出力とレビューの回答。
6. **影響。** `python3 -m kb planning impact <束>` を実行します。整理版の frontmatter にあるトピックノードから `audit/impact.md`(生成ファイル、根拠層)を書きます: そのノードの仕様、仕様が受け持つコード、そのコードに一段階依存するコードとテスト(さらに見るなら `--depth`)、そのノードの決定、同じノードの別の企画。要約行とぶつかるもの — 企画が食い違う現行の決定、同じノードの別の企画 — を人に見せます。仕様を直すか決定を置き換えるかは人が決めます。ノードがなければ、企画がどのトピックノードに属するかを尋ねます。証拠: 要約行。
7. **次へ。** `python3 -m kb skills next strata.planning`: 受け入れ基準なら strata.spec、strata.decision、または何もしない。**決定への近道:** 原典が決定のための議題にすぎないときは、整理版を飛ばして事実リストから直接 strata.spec か strata.decision に進みます。

## 注入の境界

注入・共有されるもの: 整理版と決定。根拠としてだけ残るもの: `source/`、`audit/`、そして `category: source` または `audit` と印の付いたもの。境界はパスと分類の両方で守ります(DEC-2026-11-01-05)。知識検索は根拠を飛ばします。`python3 -m kb planning boundary` は GitHub コネクタ用の除外パスと share.yaml の `never` 行を出力し、`--list` は注入ツールが読んでよい整理版を出力します。Notion は kit の外です: 整理版のページと原典のページを分け、コネクタは整理版の側に向けます。

## 言い訳と反論

| 考え | 反論 |
|---|---|
| 「原典は短いので、要約で十分だ。」 | 要約は何を捨てるかを黙って決めます。事実リストなら、捨てたものも行き先付きの行として見えます。 |
| 「テーブル名を書けば規則がはっきりする。」 | 企画を一つの実装に縛り、注入にも漏れ出します。'code' の行に移してください。 |
| 「自分で書いたのだから、自分でチェックできる。」 | 書いたコンテキストは甘くなります。新しいコンテキストでチェックしてください。 |
| 「衝突は明らかだから、新しい原典を選べばいい。」 | それはポリシーの選択です。欠陥として記録し、尋ねてください。 |

## 警告サイン

- 本人がツリーを確認する前に書かれた整理版。
- 原典にある規則の数より行が少ない事実リスト。
- 行き先のない、または二重に数えられた対照表の行。
- テーブル、クラス、API パス、ベンダーの名前が入った整理版。
- その場で書き換えられた原典。

## 検証

- `kb planning check` が、行き先の欠落、二重カウント、切れた引き渡し、コード表現を示さない。
- ツリー、隔離、欠陥の扱いに本人の答えが記されている。
- バンドルに対して新しいコンテキストでのレビューが行われた。
- 原典が手を加えられないまま `source/` の下にある。
