# 構造先払いの原則

> 正本: strata-kit `core/docs/ja/architecture/prepaid-structure.md` — strata `docs/03-architecture/prepaid-structure.md` から移管 (オーダー 2026.10.29-06、2026-10-29)。ルール YAML は `core/rules/`。

> レイヤールールの機械可読の正本: `core/rules/layer-rules.yaml` / レイヤー別の説明: `core/docs/ja/architecture/backend-cqrs.md`
> この文書は「なぜこの構造を最初から備えるのか」を説明する上位の原則である。(DEC-2026-09-30-01, strata)

## 要約

- **原則:** いま払う構造のコストが、後の変更コストを十分に相殺するなら、その構造は最初から備える。相殺できない構造は、必要になるまで作らない。
- **判定基準は三つである:** いまかかるコスト、後でその変更が必要になったときにかかるコスト、その変更が実際に起こる可能性。
- **規模に応じてレイヤーを減らさない。** レイヤーの役割と依存方向はすべての規模で同じである。規模によって変わるのはドメイン数とデプロイ単位だけである。
- **モノリスから MSA へ移るときにレイヤーがほとんど変わらないようにすることが目標である。** レイヤーが覆えないコストはデータ所有、ドメインをまたぐ書き込み、ドメインをまたぐ読み取りの三か所に集中するので、この三つのルールもあらかじめ決めておく。
- **先払いした構造は、強制して初めて維持される。** コンパイラや CI が止めない境界は、時間とともに少しずつ漏れ出し、その分だけ前払いした価値が失われる。

## 判定リスト

### 常に備える構造

| 構造 | いまかかるコスト | 相殺する変更コスト |
|---|---|---|
| レイヤーの役割と一方向の依存 | ファイル配置と呼び出し経路をルールに合わせる手間 | 機能を移したり切り出したりするとき、何が一緒に付いてくるか予測できなくなるコスト |
| コマンドとクエリを分けたサービス (CQS) | サービスファイルが倍になり、トランザクションの位置を意識する必要がある | 読み取りモデルを切り離したり、キャッシュ・レプリカへ移したりするときに、書き込みコードまで解体しなければならないコスト |
| エンティティモジュールとサービスモジュールに分けたビルドモジュール | ビルド設定、モジュール間の依存宣言、トランザクション・同期・非同期処理の複雑さ | サービスを分離するときにコードの境界を新たに引くコスト。モジュールがそのままデプロイ単位の候補になる |
| 外部システム境界のポートとアダプター (DB、メッセージング、外部 API) | 境界ごとにインターフェース一つと実装一つ | 外部システムの入れ替え、同一プロセス内の呼び出しをネットワーク呼び出しに変えるコスト |

### 必要なときだけ備える構造

| 構造 | 備える時点 |
|---|---|
| イベントソーシング (`es-cqrs` 変形) | 監査証跡、過去時点の再構成、イベントの再生が要件として確認されたとき |
| 別の読み取りストア | 参照負荷や参照モデルが書き込みモデルと実際に乖離したとき |

### 備えない構造

| 構造 | 理由 |
|---|---|
| 内部レイヤーごとに置くインターフェース抽象化 | 内部実装を入れ替えることはほとんどなく、相殺する変更コストがない。レイヤー方向のルールだけで同じ効果が得られる |
| 全面的なヘキサゴナル構造 | ポートとアダプターが価値を生むのは外部境界だけである。内部まで広げるとコストが増えるだけである |

## レイヤーが覆えない三つの境界

モノリスからサービスを切り出すとき、レイヤーのコードはほぼそのまま移る。残るコストは下の三か所で生じる。この三つは最初からルールとして定めておく。

### データ所有

- 一つのテーブルは一つのエンティティモジュールが所有する。テーブルのスキーマ変更履歴(changelog)もそのモジュールが所有する。
- 他のモジュールはそのテーブルに直接書き込まない。書き込みは所有モジュールのコマンドサービスを経由する。
- 理由: サービスを分離するときに DB を分けるコストは、「誰がどのテーブルに書くか」が散らばっているほど大きくなる。

### ドメインをまたぐ書き込み

- 二つのドメインの書き込みを一つのトランザクションに束ねない。一つのドメインの書き込みが終わったあとでイベントを発行し、他のドメインはそのイベントを受けて自分の書き込みを行う。
- 発行の記録はトランザクションの中で一緒に保存する(outbox 方式、例: Spring Modulith のイベント発行テーブル)。モノリスでは同一プロセス内の配信、MSA ではブローカー経由の配信に変わる箇所が、ここ一か所になる。
- 理由: 一つのトランザクションに束ねられた二つのドメインは、サービスに分けた瞬間に分散トランザクションの問題になる。

### ドメインをまたぐ読み取り

- 他のドメインのデータを読む経路は、ドメインごとに一か所に決める。参照専用の窓口(参照サービスまたは調整レイヤー)、または DB 水準の外部テーブル参照(FDW など)のうち一つを選び、混ぜない。
- 他のドメインのエンティティ型を直接持ち込まない。参照結果は自分のドメインの型で受け取る。
- 理由: 読み取り経路が一か所なら、サービスを分けるときにその一か所だけをネットワーク参照に変えればよい。

## 規模とデプロイ単位

- 小さなプロジェクトでも、レイヤーとモジュールの構造は同じである。ドメインが一つだけなら、ドメインモジュールが一つあるだけである。
- モノリスと MSA の違いは「モジュールをいくつ一つのプロセスにまとめてデプロイするか」で見る。モジュールを別のプロセスに移すことは、上の三つの境界の伝達方式を変えることになる。
- 予算と運用の事情に応じて、デプロイ単位はいつでも統合も分割もできる。レイヤーとモジュールの境界を守る限り、この選択はコード構造を作り直す決定ではない。

## 言語別の安価なコンパイル境界

先払いコストを最も下げる方法は、言語とビルドツールがすでに提供している境界を使うことである。各言語バインディングは「モジュール境界を何で作り、モジュール内のレイヤー方向を何で止めるか」を記す。

| 言語 | モジュール境界 (コンパイラ強制) | モジュール内のレイヤー方向 | 循環 |
|---|---|---|---|
| Kotlin / Java | Gradle マルチモジュール (`implementation` が基本) | ArchUnit (CI で遮断) | モジュール循環は Gradle が拒否 |
| Go | モジュールと `internal/` パッケージ | depguard などの import ルール | パッケージの循環 import はコンパイルエラー |
| Rust | cargo workspace のクレート | クレート分離またはモジュール可視性 (`pub(crate)`) | クレート循環は cargo が拒否 |
| TypeScript / JavaScript | ワークスペースパッケージ (`exports` で公開面を制限) | dependency-cruiser、eslint-plugin-boundaries | パッケージマネージャーが許すため `no-circular` ルールが必須 |
| Swift | SwiftPM のパッケージ・ターゲット | ターゲット分離 + チェッカー (`profiles/frontend.swiftui/enforcement/`) | ターゲット循環は SwiftPM が拒否 |

バインディング文書は `profiles/<id>/docs/ja/` にある。新しい言語バインディングは、実際のプロジェクトができたときに追加する。

## フロントエンドに同じ原則を適用した例

- トークン三段(生の値 → エイリアス → コンポーネント)は、エイリアス層を先払いして、テーマやブランドを変えるコストをエイリアス定義一つに減らす構造である。詳細: `core/docs/ja/architecture/frontend-design-contract.md`
- コンポーネント階層は上から下へだけ取り込む。詳細: `core/docs/ja/architecture/frontend-web.md`

## 先払いの保全

- モジュール境界はビルドツールが、モジュール内のレイヤー方向は CI のアーキテクチャテストが止める。編集時点のフックは素早いフィードバックにすぎず、正本の判定ではない。
- 既存のコードに違反が溜まっているなら、ベースラインとして固定し、新しく生じる違反だけを止める。ベースラインは減る方向にだけ更新する。

## 根拠事例 (あるバックエンドプロジェクト, 2026-09)

- 注文モジュールの 3.0 設計を請求 (billing) モジュールに移すとき、作業はエンティティ・ドキュメント・サービスモジュールを新しく作り、ゲートウェイ経路を回すことで終わった。レイヤールールとサービスコードの形は変わらなかった (そのプロジェクトの 2026-09-08 の決定)。
- 実際に悩んだコストは、同じ DB に二つのモジュールを共存させる仕組みとデータ移動だった。この経験が「データ所有」境界をルールに引き上げた根拠である。
- 2026-07 の ArchUnit 実測で、モジュール内のレイヤー違反が 1,500 件近く出た。モジュール境界はコンパイラが守ったが、モジュール内の境界は警告にしか頼っていなかったからである。「先払いの保全」節の根拠である。
