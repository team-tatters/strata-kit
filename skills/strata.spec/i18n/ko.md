# strata.spec

## 개요

변경 하나에 대한 바라는 명세를 만듭니다. 끝났을 때 무엇이 참이어야 하는지를 기준마다 검증할 수 있게 적고, 지금 시스템과 무엇이 다른지를 적습니다.

## 언제 쓰는가

변경이 요청됐는데 바라는 명세가 없을 때, 기획 문서에 인수 기준이 없을 때, 사용자가 계획과 현재 동작이 맞는지 물을 때 씁니다. 동작이 바뀌지 않는 순수 리팩터링에는 쓰지 않습니다. 계획과 동작이 맞는지 답하는 것은 읽기 전용이고, 명세를 쓰거나 고치면 단일 세션으로 올라갑니다(DEC-2026-11-01-18).

## 절차

1. 기획 출처와 변경이 닿는 as-built 문서를 읽습니다. 증거: 읽은 문서 목록.
2. 목표, 범위(포함·제외), 인수 기준(각각 증명할 증거), 적용 카드에서 온 제약, 답할 사람이 적힌 미결 질문을 씁니다. 증거: 기획 문서의 절.
3. 바라는 형상과 as-built 의 차이를 한 줄씩 적습니다. 증거: 차이 목록.
4. 새 아키텍처 결정이 필요한 기준을 표시하고 여기서 결정하지 않습니다. 증거: 표시된 항목.
5. 이 세션에서 새로 쓰거나 고친 기획 문서마다 구현 검토로 닫습니다. `implementation.status` 는 1·3단계에서 확인한 대로 적고(implemented, partial, diverged, not-implemented, superseded — unreviewed 로 두지 않음), `reviewed` 는 오늘 날짜, `spec` 은 기획을 실현하는 코드를 covers 로 가진 as-built 명세입니다. 그 코드를 맡은 명세가 없으면 `spec` 을 조용히 비우지 말고 차이 목록에 한 줄("<경로> 를 맡은 명세 없음")로 적습니다. 커버리지 게이트는 바뀐 코드에서 `spec` 을 거슬러 기획에 닿습니다. `spec` 이 없는 기획은 게이트에 보이지 않습니다. 증거: implementation 블록. 검토에서 기획과 구현이 어긋나면 판정 요청을 남기고(`python3 -m kb divergence add`, 게이트의 재대조 행은 `kb coverage-gate --divergence-inbox`) 사람에게 묻습니다. 판정을 스스로 고르지 않습니다(document-format 의 기획 작성 규칙, DEC-2026-10-31-35).

## 합리화

| 생각 | 반박 |
|---|---|
| "사용자가 이미 대화에서 설명했다." | 대화는 영속 산출물이 아닙니다. 기획 문서에 쓰지 않으면 다음 세션은 모릅니다. |
| "인수 기준은 구현 뒤에 써도 된다." | 그러면 원한 것이 아니라 만든 것을 적게 됩니다. 먼저 씁니다. |
| "차이 목록은 뻔하다." | 그래도 씁니다. 수렴 게이트는 기억이 아니라 목록을 읽습니다. |
| "구현 검토는 나중에 해도 된다." | 나중은 잘 오지 않습니다. 들여온 기획 대부분이 미검토로 남아 있습니다. 이 세션이 건드린 기획은 코드를 열어 둔 지금 검토합니다. |

## 적신호

- 증거가 없는 기준.
- as-built 문서를 직접 고치는 명세.
- 문서 없이 '논의한 대로 구현'.
- 미검토로 닫은 기획 문서, 또는 `spec` 도 없고 그 이유를 적은 차이 줄도 없는 기획 문서.

## 검증

- 모든 기준에 증거가 있다.
- 차이 목록이 있다.
- 미결 질문에 답할 사람이 있다.
- 건드린 기획 문서마다 implementation 블록(status, reviewed, spec 또는 명세 없음 차이 줄)이 있다.
