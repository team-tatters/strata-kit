# Knowledge Base — Vault structure

> Canonical: strata-kit `core/docs/en/knowledge-base/vault-structure.md` (migrated 2026-10-29 from strata `docs/07-knowledge-base/vault-structure.md`, DEC-2026-10-29-11).

## Overview

The vault is an Obsidian-compatible knowledge base shared by all projects.
It is managed as an independent Git repository, separate from project code.

## Three-layer model (Archive / Knowledge / Index)

All content in the vault belongs to one of three layers, and each layer has its own maintenance discipline (DEC-2026-08-19-04):

| Layer | Directory | Discipline |
|---|---|---|
| **Archive** | `projects/*/sessions/`, `projects/*/tasks/`, `projects/*/relays/` | append-only. Write-once is **normal** — no duty to revise or link. An evidence store, not a KB |
| **Planning** (Archive variant) | `projects/*/planning/{source}/` | Original planning text (`type: planning`) brought in from an external planning tool (Notion, etc.). **The original sections are immutable** (Archive discipline); only the `## 구현 검토` section (implementation review) at the end of the document is updated — it records, per policy item, whether it is implemented, how it differs from the plan, and the evidence, in a table, and is classified by the frontmatter `implementation.status`. Policies with substance are distilled into Knowledge specifications, and the `sources:` of that specification points at the original (DEC-2026-09-09-01) |
| **Knowledge** | `projects/*/knowledge-base/`, `patterns/`, `_index/glossary.md` | **Duty to update in place** — `updated:` is required on every revision, and a source link to the supporting Archive document (`sources:` frontmatter) is required |
| **Index** | `_index/`, each `_index.md`, DEC notes in `projects/*/decisions/`, node pages in `projects/*/nodes/` | **Generated only — no hand edits.** Regenerated from the canonical source (records, frontmatter, toc.yaml) (DEC projection generator, node page generator — implementation mapping: `python3 -m kb --help` · `core/docs/en/kb-engine.md`) |

Knowledge promotion (Archive → Knowledge) is done by a distillation session and goes through the Decision Inbox gate.
Updating an existing Knowledge document takes priority over creating a new one (living document principle).

### Roles and locations of the three document kinds (DEC-2026-09-30-03)

| Document | What it holds | Where it lives | Default search |
|---|---|---|---|
| Spec (decision) | The decision made at implementation time about code and implementation requirements, and its reason, the target code symbols, and whether it is current or superseded | decision record (Tier P) → DEC note mirror | before indexing — read the index (`decisions.yaml`) and DEC notes directly (adding them to the index is a follow-up) |
| KB (Knowledge) | The final shape of a service and its domain, explained as a table of contents and flow that people can understand | `knowledge-base/`, table of contents in `_meta/toc.yaml` | included |
| Work history (Archive·Planning) | Session records, task specifications, dated diagnoses and reports, original text from external planning | `sessions/`, `tasks/`, `relays/`, `planning/` | excluded (only on explicit request) |

- **One KB document per table-of-contents slot.** Do not create a new document on the same topic; rewrite the existing one. If it is unavoidably replaced by a new document, close the old one with `status: superseded` + `superseded_by`.
- **Dated reports, diagnoses and snapshots are not KB.** A document whose filename or title contains a date (such as `*-2026-09-16.md`) records the facts of that day, so it goes in the work history (`tasks/{date}/` or `sessions/`). The KB reflects only the final shape that changed as a result, and points at the report with `sources:`.
- **The default search looks only at the KB.** Work history is included only when explicitly requested from the search tool (`search_docs(include_history=true)` or specifying `category`, CLI `--include-history`). This is so that history does not push the canonical documents out of search results.

The key that cuts across the three layers is the **topic node**. A node is a unit of the table of contents that people read, and its canonical source is the project's `_meta/toc.yaml`.
A document declares its membership with the frontmatter `nodes:`, and the node page is generated by **joining** the Knowledge (final shape, policy), decisions and Archive (work history) that point at that node.
A node page is not a promotion. It writes nothing new; it only gathers what already exists onto one screen, and when there is a hole it leaves the hole visible. That hole is the visualization of what is missing.

## Directory structure

```
vault/
├── .obsidian/           Obsidian app settings (shared, git-tracked)
│   └── plugins/         Plugin settings for Custom Sort, Dataview, etc.
├── .kb/                 ★ KB index management
│   ├── manifest.json    Per-file SHA256 hashes (git-tracked)
│   ├── schema.sql       DB schema definition (git-tracked)
│   └── store.sqlite     KB store (strata-kit kb, .gitignore — the legacy kb.sqlite was removed by DEC-2026-10-28-13)
├── .local/              Per-machine settings (.gitignore)
│   └── resolved-paths.yaml
├── .gitignore
├── env-config.yaml      List of registered machine aliases (no paths)
│
├── _index/              MOC (Map of Content)
│   ├── projects.md      Project list + links
│   ├── decisions.md     Cross-project ADR index
│   ├── patterns.md      Pattern/lesson index
│   └── glossary.md      Domain glossary
│
├── _meta/               ★ Global settings
│   └── taxonomy.yaml    Classification scheme definition (categories, types, tags)

├── projects/            Per-project knowledge
│   └── {project-name}/

│       ├── _meta/               Project settings

│       │   └── toc.yaml         ★ Topic node tree (canonical source of the human-readable table of contents) — topic axis
│       ├── knowledge-base/      ★ Project KB (indexed)
│       │   ├── _index.md        MOC (Dataview dynamic table of contents)
```

## Naming rules

| Target | Format | Example |
|---|---|---|
| Project directory | kebab-case | `my-api-server` |
| Document filename | kebab-case.md | `auth-strategy.md` |
| DEC note (generated) | DEC-YYYY-MM-DD-NN.md | `DEC-2026-08-19-01.md` |
| Node page (generated) | {node-id}.md — the node id as is, including dots (.) | `orders.checkout-v2.coupon.md` |
| Session document | session-YYYY-MM-DD-{slug}.md | `session-2026-08-19-vault-restructure.md` |
| MOC file | singular noun | `projects.md`, `glossary.md` |

Session filenames use only the single format above — the `handoff-*` prefix, unprefixed date filenames and `.yaml` session files are retired (legacy ones are migration targets). The slug, not a sequence number (NN), is the real identifier.

## Stable ID (frontmatter `id:`)

Every vault document has a stable ID in its frontmatter that does not change when the document is moved or renamed:

```yaml
id: "kb-shop-api-order-concepts"   # {prefix}-{project}-{slug} — immutable after creation
aliases: ["old filename"]              # on move or rename, keeps the original identifier (absorbs Obsidian unlinked mentions)
```

The prefixes cover every document class (reflecting the cross-review of 2026-08-19):

| Prefix | Target | Example |
|---|---|---|
| `kb` | documents in knowledge-base/ and patterns/ | `kb-shop-api-order-concepts` |
| `session` | sessions/ (handoffs · ledger) | `session-strata-2026-08-19-vault-restructure` |
| `order` | work order `_order.md` | `order-strata-2026.08.19-01` |
| `task` | task specification documents | `task-strata-2026.08.19-01-task-03` |
| `dec` | DEC notes (generated) | `dec-strata-2026-08-19-01` |
| `relay` | relays/ packet·feedback | `relay-strata-2026-08-19-task01-core-spec-review` |
| `moc` | MOCs in `_index/` and each `_index.md` | `moc-shop-api-knowledge-base` |
| `node` | node pages in `nodes/` (generated) | `node-shop-api-orders.checkout-v2.coupon` |
| `plan` | planning documents in `planning/` (imported) | `plan-shop-api-0123456789abcdef0123456789abcdef` — the slug is the source (Notion) id, immutable across re-imports |
| `doc` | any other document not covered above | `doc-vault-env-config` |

- **The {project} value**: under `projects/{name}/` it is that project name. **Cross-project documents** (`patterns/`, `references/`, `_index/`, the vault root) use `vault` (e.g. `kb-vault-{slug}`, `moc-vault-decisions`).
- A path is only a means of navigation, not a long-term identity. The identity of links and references is carried by `id:`.
- On migration (move or rename), keep the `id:` and add the old filename to `aliases:`.
- **A node id is a different namespace from a document id.** It is a dot-joined (.) path starting from the ancestors, like `orders.checkout-v2.coupon`, and does not follow the prefix scheme above. A document writes node ids in its `nodes:` field, and only the **document** id of a node page enters the prefix scheme, as `node-{project}-{node-id}`. Dots in the slug are allowed only under the `node` prefix.

## KB category scheme

Defined in taxonomy.yaml, made up of four categories:

| Category | Purpose | depth limit | Main types |
|----------|------|:---:|-----------|
| `domain` | Business domain knowledge | 3 | concept, specification, flow |
| `architecture` | Design decisions, API, infrastructure, constraints | 2 | specification, decision, overview, constraint |
| `guides` | Onboarding, conventions, troubleshooting | 2 | guide, pattern, runbook |
| `references` | External standards, specification references | 2 | reference, glossary |

- No NN prefix — ordering follows the taxonomy `order` field
- The category is derived from the directory (not written in frontmatter)
- The children of the `domain` category are defined in the project taxonomy
- Detailed rules: `templates/vault/_meta/taxonomy.yaml`

The category is the **directory axis** (where a document is placed), and the topic node is the **topic axis** (what a document is about). The two are separate.
The category is not written in frontmatter because it would duplicate the path, but `nodes:` is information that cannot be derived from the path, so it is not a duplicate. One document can belong to several nodes, and a node does not create a directory.
Canonical source and rules of the node tree: the project's `_meta/toc.yaml`; format rules are in the `topic_nodes` section of the global taxonomy.

## Project onboarding procedure

When registering a new project in the vault:

1. Create the `vault/projects/{project-name}/` directory
2. Write `overview.md` (with the required frontmatter; see document-format.md)
3. Update `_index/projects.md` (Index layer — replaced by regeneration once it becomes generated)
4. Create `_meta/taxonomy.yaml` (defines the project's domain topics)
5. Create `_meta/toc.yaml` (topic node tree — a single first node is enough. The starting point is when documents begin to have `nodes:`)
6. Create the category directories under `knowledge-base/` (`domain/`, `architecture/`, `guides/`, `references/`)
7. Create the `sessions/` and `tasks/` directories. For a detached profile project, include `strata/` (Tier P) — the `profile.yaml` manifest is required (core/docs/en/environment/data-placement.md §1.5). `decisions/` and `nodes/` are created by the generators

### Minimum content of overview.md

```markdown
---
title: "{project name}"
type: overview
project: {project-name}
tags: [{tech stack tags}]
created: {YYYY-MM-DD}
updated: {YYYY-MM-DD}
status: active
---

## Purpose
{1-2 sentences on the project's purpose}

## Tech stack
- Language: {language}
- Framework: {framework}
- DB: {database}

## Strata layer mapping
{Mapping of this project's directories → Strata layers}
```

## What is never included

- Source code (code snippets are allowed as an exception)
- Build artifacts
- Environment-specific absolute paths
- Secrets, keys, tokens
- Raw handoff YAML (store only a summary)

Exception: the repository **relative paths, symbols, endpoints and table names** in the frontmatter `covers:` are pointers, not code, so they are allowed. Absolute paths and code bodies are still forbidden.
