# design.brief

## 概要

これは本人のデザイン段階です。文書、実物、画像、投稿、画面 — 何をデザインするにしても、作業はブリーフから始まります: 何のためのものか、誰が見るか、どの媒体か、どんな制約の下か、何を参照するか、何が成り立てば完了か。ブリーフは本人のものです。エージェントは尋ねて書き留めるだけで、好みを決めません。デザインは本人の好みと、それを表現する技法(ガラスのような面、浮き上がった柔らかい影、重ねた枠線と陰影)に支えられます。ブリーフには、この作業で使うものを名前で書きます。

フロントエンドのデザイン契約(core/docs/<locale>/architecture/frontend-design-contract.md)は別のものです。決まったデザインをコードに運ぶ技術的な流れです。このパックはそれに従わず、それを変えもしません(DEC-2026-11-01-09)。両者が出会うのは一か所です: 成果物が製品に入るとき、契約が `design_ref` でそれを指します。本人の表現を製品のトークンに置き換えるのは実装の仕事です。

## 使う場面

本人が媒体を問わず何かをデザインしようとしているとき、仕様やリリースにデザインが必要なとき、本人がデザインをその目的に照らして判定したいとき。仕様を書く作業(strata.spec)や、画面の実装(strata.build-task)には使いません。デザインについて話し合うだけなら読み取り専用で、ブリーフを書くときに単一セッションへ上がります(DEC-2026-11-01-18)。

## 手順

1. **ブリーフ。** 一度に一つずつ尋ね、七つの節を書きます: Purpose、Audience、Medium and format、Constraints、References、Acceptance criteria、Deliverable(目的、見る人、媒体と形式、制約、参照、受け入れ基準、成果物)。目的は、何をデザインするのかから聞き始めます — ウェブページ、アプリ画面、スライド、レポート、インフォグラフィック、ポスター、画像や投稿、実物、その他。ブリーフの frontmatter に `category`(`web`、`app`、`slides`、`report`、`infographic`、`poster`、`image`、`post`、`object`、`other`)としても書きます。次にこの作品が伝えるべき一文、そしてコンテンツの順序 — 必ず入れるものと外してよいもの — を聞きます。カテゴリが手順3のアダプターを決めます。答えのない節には不明と書きます。証拠: ブリーフとそのカテゴリ。
2. **参照。** 参照ごとに、本人が最初に何に気づいたか、その中の何がそう感じさせるのか、それがこの作業に入るべきかを尋ねます。答えをリンクの横に書きます。プロジェクトやブランドに好みのノートと表現のノート(design.taste)があれば、この作業が支えにする好みの行(#tag)と技法を名前で挙げます。本人が書かれたとおりに承認した反応や却下は、design.taste を通じてこのブリーフから出た信号として好みのノートに入ります。証拠: References の節。
3. **作る、または任せる。** 本人がデザインするか、エージェントがブリーフの範囲で下書きを作ります。エージェントが出す案にはエージェントのものだと明記し、選ぶのは本人です。ブリーフのカテゴリに合うアダプターを `data/adapters.md` で読みます: スライド・レポート・インフォグラフィックは文書アダプター(論証、アクションタイトル、グラフと構造の選び方)、ウェブとアプリは本人が外部のデザインスキルを選べばそれを、選ばなければそのファイルの短い代替規則を使います — 両方は使いません。成果物がウェブページやアプリ画面で、本人が望むなら、本人がすでにインストールしているデザインスキルを使います — たとえば Taste Skill(Leonxlnx/taste-skill、`design-taste-frontend`)や Impeccable(pbakaus/impeccable)。どれを使うか尋ね、自分でインストールはしません。ブリーフの目的・見る人・制約と、あればプロジェクト・ブランドのプリミティブと技法を渡します(Taste Skill は `--keep palette,type`、Impeccable は `DESIGN.md`)。そのスキルが選んだものはエージェント側の案であり、本人の好みではありません。決めるのは引き続きブリーフの受け入れ基準と本人の判定です(DEC-2026-11-01-12)。証拠: 下書き、使ったスキル(あれば)、本人の選択。
4. **判定。** `data/adapters.md` の共通チェックを、エージェントの提案として受け入れ基準の候補に出します。本人が選んだものだけが基準に入ります。受け入れ基準ごとに本人が判定し、その判定を書きます。満たされなかった基準は、それが現れた箇所だけでなく、原因となった段階 — 目的、コンテンツの順序、階層、レイアウト、値、焦点 — に作業を戻します。Deliverable の節で `design_ref`(`kind`、`ref`、`version`)を使って結果を指します。結果が製品に入るときは、その `design_ref` から製品自身の手順が引き継ぎます。証拠: 判定と参照先。
5. **次へ。** `python3 -m kb skills next design.brief`: 記録すべき反応や却下が出たなら design.taste、成果物が製品に入るなら strata.order、strata.review、または何もしない。

## 言い訳と反論

| 考え | 反論 |
|---|---|
| 「ただのポスターだ。ブリーフは大げさだ。」 | 五行で足ります。目的と見る人がなければ、完了したかどうか誰にも言えません。 |
| 「ここで何が良く見えるかはわかっている。」 | それはモデルが見てきたものの平均です。好みとは、本人が自分の参照に示した反応です。尋ねてください。 |
| 「参照リンクがあれば十分だ。」 | リンクは何が大事だったかを語りません。本人が何に反応したかを書いてください。 |
| 「製品のトークンのルールがこれを形作るべきだ。」 | ここではそうではありません。契約は design_ref で成果物を受け取り、置き換えるのは実装です。 |
| 「Medium and format の節にもう何かは書いてある。」 | その節にあるのは大きさとファイル形式です。何をデザインするのかがアダプターと外部スキルを決めます。先に尋ねてください。 |
| 「アダプターには良い初期値があるから、それを当てはめよう。」 | それは作りの点検と出発点であり、その人の見た目ではありません。本人の参照と好みが先です。 |

## 警告サイン

- ブリーフなしで渡された成果物。
- 本人が一度も言っていない目的、見る人、受け入れ基準。
- リンクだけが並んだ参照。
- エージェントが選んだ見た目が本人の好みとして記録されている。

## 検証

- ブリーフに本人の言葉による七つの節とカテゴリがあり、不明な点は印が付いている。
- 受け入れ基準ごとに本人の判定がある。
- Deliverable の節が design_ref で結果を指している。
