# strata.planning

## 개요

기획 단계는 필터입니다(DEC-2026-11-01-04). 기획 원문에는 정해지지 않은 이야기와 코드와 규칙이 섞여 있어서, 그대로 주입하면 뒤에 읽는 모두(검색, Onyx 같은 주입 도구, 동료)가 가비지를 읽습니다. 그래서 원문을 바로 요약하지 않습니다. 한 행에 사실 하나로 쪼개고, 모든 행에 행선지를 붙입니다. 주입·공유되는 것은 정리본 — 사람이 관찰할 규칙을 적은 PRD 와 구현이 바뀌어도 유지될 보장을 적은 Logical Tech Spec — 과 결정 기록뿐이고, 원문과 작업 표는 근거로 남습니다. **기획 문서에는 코드와 아키텍처를 쓰지 않습니다.** 테이블, 컬럼, 클래스, 서비스, API 경로, HTTP 코드, 프레임워크, 벤더는 '코드' 행선지로 보내서 명세·오더·결정의 재료로 씁니다.

## 언제 쓰는가

바깥의 기획 원천이 들어왔을 때, 아이디어 노트(ideation.shape)가 기획이 될 준비가 됐을 때, 기존 묶음의 대조표를 확인해야 할 때 씁니다. 이미 정리된 기획에 인수 기준을 쓰는 일(strata.spec)이나 아키텍처 선택(strata.decision)에는 쓰지 않습니다. 작업 모드는 원천을 읽기만 하는 동안 읽기 전용이고, 묶음을 쓰면 단일 세션으로 올라가며, 묶음이 세션을 넘기면 여러 세션입니다 — 세션이 끝날 때마다 핸드오프(DEC-2026-11-01-18).

## 절차

1. **원천을 사실 목록으로.** 원천은 손대지 않고 `source/` 아래에 둡니다(또는 `category: source` 로 표시). `audit/facts.md` 에 규칙·권한·상태 전이·예외·데이터·화면·인수 기준·결정·가정·의존·개정 이력을 한 행에 사실 하나로 적습니다. 열은 이 순서입니다: `# | 원천 위치 | 유형 | 내용(원천의 뜻을 바꾸지 않은 한 문장) | 역할(기획·명세·코드·배경·중복) | 축 | 하위 주제`. 축은 규칙이 답해야 할 다섯 질문 — 동일성, 시간, 파생, 소멸, 충돌 — 이고, 해당 없으면 `해당 없음` 이라고 적습니다. 증거: 사실 목록.
2. **트리와 결정.** 하위 주제를 모아 트리 초안을 만들고, 본문을 쓰기 전에 사람의 확인을 받습니다. 원천끼리 다르거나 이후 결정과 부딪히는 것은 질문으로 올리고, 아키텍처를 묶는 답은 strata.decision 으로 기록합니다. 증거: 확인된 트리, 질문과 답.
3. **정리본을 쓰며 모든 행에 행선지를 붙입니다.** `audit/coverage.md`(`# | 원천 위치 | 행선지 | 비고`)에서 사실마다 일곱 행선지 가운데 정확히 하나를 붙입니다: `<문서> R<n>`(정리본에 반영), `격리:<묶음>`, `결함:<내용>`, `코드`, `배경`, `중복:#<n>`, `범위 밖:<묶음>`(받는 묶음의 대조표에도 같은 행이 있어야 함). 모순과 공백은 `audit/defects.md` 에 정리본이 어떻게 처리했는지와 함께 적습니다. PRD 와 Tech Spec 에는 `planning_doc: prd` / `tech-spec` 을 답니다. 증거: 대조표.
4. **복잡도 검토.** 기능의 정책이 사람이 기억할 양을 넘으면(검사가 PRD 800단어·규칙 10개, Tech Spec 1,200단어 초과를 보이면) 상태별 정책 표를 만들고 단계나 상태를 격리하는 안을 냅니다. 격리는 정책을 바꾸므로 사람이 정합니다. 옮긴 규칙은 `audit/isolated.md` 로 갑니다. 증거: 격리안과 결정.
5. **새 컨텍스트에서 검사.** `python3 -m kb planning check <묶음>` 을 돌립니다: 행선지 없는 행, 두 번 센 행, 받는 쪽에 없는 넘긴 행, 축이 빈 규칙 행, 상한, 정리본의 코드 표현(정리본에서만 — 원문과 audit 는 무엇이든 적어도 됩니다). 고치고 다시 돌립니다. 그다음 묶음을 strata.review 로 보내 검사만 받습니다. 묶음을 쓴 컨텍스트는 자기 글에 관대합니다. 증거: 검사 출력과 리뷰 답.
6. **영향.** `python3 -m kb planning impact <묶음>` 을 실행합니다. 정리본 frontmatter 의 주제 노드에서 출발해 `audit/impact.md`(생성 파일, 근거 층)를 씁니다: 그 노드의 명세, 명세가 맡은 코드, 그 코드에 한 단계 기대는 코드와 시험(더 보려면 `--depth`), 그 노드의 결정, 같은 노드의 다른 기획. 사용자에게 요약 줄과 부딪히는 것 — 기획이 어긋나는 현행 결정, 같은 노드의 다른 기획 — 을 보입니다. 명세를 고칠지 결정을 대체할지는 사용자가 정합니다. 노드가 없으면 기획이 어느 주제 노드에 속하는지 묻습니다. 증거: 요약 줄.
7. **다음.** `python3 -m kb skills next strata.planning`: 인수 기준은 strata.spec, strata.decision, 또는 아무것도 안 함. **결정 지름길:** 원천이 결정 자리의 안건뿐이면 정리본을 건너뛰고 사실 목록에서 바로 strata.spec 이나 strata.decision 으로 갑니다.

## 주입 경계

주입·공유되는 것: 정리본과 결정. 근거로만 남는 것: `source/`, `audit/`, 그리고 `category: source`·`audit` 로 표시된 문서. 경계는 경로와 분류 둘 다로 지킵니다(DEC-2026-11-01-05). 지식 검색은 근거를 건너뜁니다. `python3 -m kb planning boundary` 가 GitHub 커넥터용 제외 경로와 share.yaml `never` 줄을 내고, `--list` 가 주입 도구가 읽어도 되는 정리본을 냅니다. Notion 은 kit 밖입니다: 정리본을 게시할 페이지와 원문 페이지를 나누고 커넥터는 정리본 쪽을 가리키게 둡니다.

## 합리화

| 생각 | 반박 |
|---|---|
| "원천이 짧으니 요약이면 충분해." | 요약은 무엇을 버릴지 말없이 정합니다. 사실 목록은 버린 것마다 행선지가 붙은 행으로 보입니다. |
| "테이블 이름을 쓰면 규칙이 더 분명해." | 기획을 한 구현에 묶고 주입으로 새어 나갑니다. '코드' 행으로 옮기세요. |
| "내가 썼으니 내가 검사해도 돼." | 쓴 컨텍스트는 관대합니다. 새 컨텍스트에서 검사하세요. |
| "충돌이 뻔하니 새 원천을 고르면 돼." | 그것은 정책 선택입니다. 결함으로 적고 물으세요. |

## 적신호

- 사람이 트리를 확인하기 전에 쓴 정리본.
- 원천의 규칙 수보다 행이 적은 사실 목록.
- 행선지가 없거나 두 번 센 대조표 행.
- 테이블, 클래스, API 경로, 벤더 이름이 들어간 정리본.
- 제자리에서 고친 원천.

## 검증

- `kb planning check` 가 행선지 없는 행, 두 번 센 행, 끊긴 넘긴 행, 코드 표현을 보이지 않는다.
- 트리, 격리, 결함 처리에 사람의 답이 적혀 있다.
- 묶음에 새 컨텍스트 리뷰가 돌았다.
- 원천이 `source/` 아래에 손대지 않은 채 있다.
