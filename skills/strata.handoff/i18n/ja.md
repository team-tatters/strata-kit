# strata.handoff

## 概要

次のセッションが、この会話なしで続けられるようにハンドオフを書きます。何を終えたか(証拠付き)、何が保留でその理由は何か、どの決定を記録したか、何に注意すべきか、個人コアに何を蒸留すべきか、です。その後、記録・検証・公開を三つの別々の手順として行います。

## 使う場面

セッションの終わり、タスクの区切り、分割やコンパクションの前、または依頼があったとき。どれだけ書くかは作業モード(using-strata)が決めます。読み取り専用は書かず、単一セッションは保留が残るときだけ、複数セッションとオーケストレーションはセッションが終わるたびに書きます。

## 手順

1. 記録: completed(ファイルと証拠付き)、in_progress(それぞれに blocker と unblocked_by)、decisions_made(DEC id)、判断の過程(ユーザーに尋ねたことと答え、覆った判断とその理由を数行で、同名の節に — DEC-2026-10-30-03)、事実と仮説(確認した事実と何で確認したか、確認できていない推定、捨てた仮説と捨てた理由 — 会話がトークン警告線を超えたか、同じ仮説で試みが二度行き詰まって再開信号で終えるセッションは必ず埋める。DEC-2026-10-31-11、session-splitting 5.1)、warnings、next_session を書きます。証拠: ハンドオフファイル。
2. 骨格: orders と kb_updates のリンクを埋めます。証拠: フロントマター。
3. 蒸留: 個人コアへの蒸留候補を挙げます。なければ理由を添えた「なし」と書きます。証拠: 候補のセクション。
4. メモリ: `python3 -m kb hygiene --memory` を実行し、このセッションが書いたか直したメモリ項目を見ます。進行状態の項目（手元の作業、次にやること、未コミット、行き詰まり）は、このハンドオフの in_progress か warnings へ移すよう提案し、人がまだ正しいと答えた項目は `verified` を今日にします。メモリから外すことは、移した後に別に尋ねます。人が項目ごとに承認したものだけ、ファイルを `_archive/` へ移し、`retired`・`retired_reason` を書き、インデックスの行を外す方法で行います。単に消しはしません（context-protocol 7 節、DEC-2026-10-31-16・17）。証拠: 提案と人の答え、または「このセッションで書いたメモリなし」。
5. 検証: カバレッジゲート、リンクチェック、未コミットレコードのチェックを実行します。証拠: 出力。ゲートが出す「仕様のない変更コード N · 候補 M · 新しい仕様が必要 K」(自前の仕様が必要なモジュールの一覧とともに)の一行をハンドオフに残します。その covers 候補は projects/<project>/_meta/covers-candidates.yaml(source: impact)で待機し、人が承認して `python3 -m kb hygiene --covers-apply` を実行すると記録されます。コードではなく知識(概念・方針・決定)を変えたセッションでは、ゲートが「再確認するコード(advisory)」も出します — 同じトピックノードの仕様の covers と、置き換えられた決定の affects です。何を再確認したか、しなかったならその理由をハンドオフに書きます。 ゲートの等級が未解決なら(FAIL・BLOCK 行 — スクリプトがハンドオフの冒頭と stderr に「no-go」行を残します)、セッションを完了として閉じません。仕様を書くか(strata.kb-update)、Tier P の gate-overrides.yaml に理由と期限を残し、どちらをしたかをハンドオフに書きます(DEC-2026-10-29-08)。
6. 公開: 列挙されたパス(ハンドオフ、ledger、ミラー)だけをステージし、セッション終了のチャネルを通じてコミットします。push の成功か失敗かを事実のとおりに報告します。 リモートが先に進んでいる場合、このセッションが書いていないファイルの上で rebase・autostash をしません。一時クローンでリモートの最新の上にこのセッションのコミットだけを載せて公開するか、止まって重なりを報告します。 コミットする前に、プロジェクトのコミット規則を読みます。プロジェクトのルートを一覧し、AGENTS.md・CLAUDE.md とそこにある規則・ノートのファイル(README、CONTRIBUTING、*NOTES*・*RULES* のような名前)を読みます。プロジェクトやユーザーの規則がハーネスの既定の指示(署名トレーラーなどの attribution)と異なる場合は、プロジェクト・ユーザーの規則に従います。

## 言い訳と反論

| 考え | 反論 |
|---|---|
| 「保留の項目は『ユーザー待ち』で十分だ。」 | 何を待っていて、何が解除するのですか。両方を書かなければ、その項目は永遠に持ち越されます。 |
| 「vault の全部をコミットしよう。」 | このセッションのパスだけです。他のセッションの変更は、あなたが公開するものではありません。 |
| 「今回は蒸留するものがない。」 | 「なし」と、その理由を書いてください。何もないことも情報です。 |

## 警告サイン

- blocker のない保留項目。
- 自分が書いていないファイルをステージした公開。
- next_session の値がないハンドオフ。

## 検証

- 保留項目が完全である。
- ゲートの出力が返信に入っている。
- 公開したパスが列挙され、push の状態が事実どおりである。
