# strata.signal

## 概述

运行阶段展示指标，不代管产品的流程。指标有两类：strata 自身的度量（kit 版本、会话、验证、交接、git），以及项目从已有流程——QA 台账、覆盖率测试用例——中只读得到的产品流程指标。其中任何一个变差时，这个技能把它连同依据留成一份笔记，并把选择交给本人：说明这个变化可能引向什么以及理由，然后记录本人的选择。

## 何时使用

当 librarian 的每日报告列出新的未处理信号时，当检查列出长期未处理的信号时，或当本人看到某个指标变差、想把它留下来时。不用于产品故障、告警或用户反馈——那些属于产品自身的功能。也不用于决定规则（strata.decision）。写笔记会把只读会话升为单会话。

## 步骤

1. **找出变化。** 运行 `python3 -m kb signals candidates --project <p>` 展示候选；`python3 -m kb indicators show --project <p>` 把产品流程指标与上一次采集对比展示。本人同意后用 `--write` 写入（librarian 的每日任务会自行写入，不带去向）。证据：候选列表或笔记路径。
2. **核对依据。** 每份笔记的依据一节都有度量值及其基准——上一个版本或上一次采集，以及阈值。如果候选所依据的太少（一个会话、一次采集），就在笔记里写明。证据：笔记的依据一节。
3. **列出可能的去向并提问。** 对每个未处理信号，给出候选及各一句理由：方法论待办项（工作方式或 kit 中的空白）、想法笔记（值得培养但还不清晰，ideation.shape）、规划文档（需要规划的工作，strata.planning）、决策（会确定规则时用 strata.decision），或丢弃（噪声、已处理）。改进产品自身的流程也和其他工作一样是规划的工作——它从本人的选择开始，而不是由这个技能写进那个流程。不替本人选择。证据：候选和问题。
4. **建立接收项，再记录选择。** 接收项只用本人认可的文字来写：待办项在加入之前先展示；想法交给 ideation.shape，规划交给 strata.planning。然后运行 `python3 -m kb signals route --project <p> <笔记> --to <条目 id 或 vault 路径> --by <本人>`。丢弃时用 `--drop "<理由>" --by <本人>`。命令会拒绝尚不存在的目标。证据：route 的输出。
5. **检查笔记。** 运行 `python3 -m kb signals check --project <p>`。修复它列出的每个问题；未处理超过 14 天的信号，以提问的方式交给本人，而不是由代理决定。证据：命令输出和退出码。

## 自我合理化

| 想法 | 反驳 |
|---|---|
| "趋势很明显，直接加待办项吧。" | 那样就没人选择过它，下一个读者也看不出它从哪里来。写下信号，展示候选，让本人来选。 |
| "本人很忙，我来选最可能的去向。" | 去向属于本人（DEC-2026-11-01-17）。保持未处理并提问；未处理的信号没有成本，错误的条目要付出清理的成本。 |
| "QA 指标变差了，我去登记缺陷或修改台账。" | QA 台账和缺陷库是产品自身的流程。kit 只读取它们；修改它们是本人选择的规划工作。 |
| "这份故障报告很重要，也留成一个信号吧。" | 故障和反馈在产品功能中有自己的位置。在这里再留一份副本会让记录分裂。 |

## 危险信号

- 未经本人认可就从信号创建的待办项、想法笔记或决策。
- decided_by 是代理或 librarian 的 routed 笔记。
- 依据中缺少比较基准的笔记。
- 从这个技能对产品自身的流程（台账、缺陷库、覆盖率报告）做的任何写入。

## 验证

- 每份新笔记都在 projects/<p>/signals/ 中，依据里有数值及其基准。
- 每份 routed 笔记都写明做出选择的人，且目标存在。
- 没有向产品自身的流程写入任何内容。
- `python3 -m kb signals check --project <p>` 以 0 退出，长期未处理的信号已交给本人询问。
