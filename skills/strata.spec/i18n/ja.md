# strata.spec

## 概要

変更のための目標仕様を作ります。完了したときに何が成り立っていなければならないかを、各基準が検証できる形で述べ、それが今のシステムの動作とどう違うかを示します。

## 使う場面

変更が依頼されたのに目標仕様がないとき、企画ドキュメントに受け入れ基準がないとき、ユーザーが計画と現在の振る舞いが一致しているかを尋ねたとき。振る舞いが変わらない純粋なリファクタリングには使いません。計画と振る舞いが一致しているかに答えるのは読み取り専用で、仕様を書く・直すときに単一セッションへ上がります(DEC-2026-11-01-18)。

## 手順

1. 企画の原本と、変更が触れる as-built のドキュメントを読みます。証拠: 読んだドキュメントの一覧。
2. 目標、スコープ(範囲内と範囲外)、受け入れ基準(それぞれ、それを証明する証拠付き)、該当するカードからの制約、それぞれに答える人を明記した未解決の質問を書きます。証拠: 企画ドキュメントのセクション。
3. 目標と as-built の差異を、一行ずつ列挙します。証拠: 差異の一覧。
4. 新たなアーキテクチャ上の決定を必要とする基準があれば印を付けます。ここでは決めません。証拠: 印を付けた項目。
5. このセッションで新しく書いた、または変更した企画ドキュメントごとに、実装レビューで締めくくります。`implementation.status` は手順1と3で確かめた結果を書き(implemented、partial、diverged、not-implemented、superseded のいずれか。unreviewed のままにしない)、`reviewed` は今日の日付、`spec` には企画を実現するコードを covers に持つ as-built 仕様を書きます。そのコードを受け持つ仕様がないときは、`spec` を黙って空けず、差異の一覧に一行(「<パス> を受け持つ仕様なし」)で書きます。カバレッジゲートは変更されたコードから `spec` をたどって企画に届きます。`spec` のない企画はゲートから見えません。証拠: implementation ブロック。 レビューで企画と実装が食い違ったら判定依頼を残し（`python3 -m kb divergence add`、ゲートの再照合行は `kb coverage-gate --divergence-inbox`）、人に尋ねます。判定を自分で選びません（document-format の企画作成規則、DEC-2026-10-31-35）。

## 言い訳と反論

| 考え | 反論 |
|---|---|
| 「ユーザーはチャットですでに説明してくれた。」 | チャットは永続的な成果物ではありません。企画ドキュメントに書かなければ、次のセッションには残りません。 |
| 「受け入れ基準は実装の後でもよい。」 | それでは、望まれたものではなく作られたものを記述することになります。先に書いてください。 |
| 「差異の一覧は自明だ。」 | それでも書いてください。収束ゲートが読むのはあなたの記憶ではなく、その一覧です。 |
| 「実装レビューは後でよい。」 | 後はなかなか来ません。取り込んだ企画の大半が未レビューのままです。このセッションが触れた企画は、コードを開いている今レビューします。 |

## 警告サイン

- 証拠が示されていない基準。
- as-built のドキュメントを直接変更する仕様。
- ドキュメントのない「話し合ったとおりに実装する」。
- 未レビューのまま閉じた企画ドキュメント、または `spec` もなく、その理由を書いた差異の行もない企画ドキュメント。

## 検証

- すべての基準に証拠が示されている。
- 差異の一覧が存在する。
- 未解決の質問に担当者が示されている。
- 触れた企画ドキュメントごとに implementation ブロック(status、reviewed、spec または仕様なしの差異の行)がある。
