# 구조 선지불 원칙

> 정본: strata-kit `core/docs/ko/architecture/prepaid-structure.md` — strata `docs/03-architecture/prepaid-structure.md` 에서 이관 (오더 2026.10.29-06, 2026-10-29). 규칙 YAML 은 `core/rules/`.

> 레이어 규칙의 기계 판독 정본: `core/rules/layer-rules.yaml` / 레이어별 설명: `core/docs/ko/architecture/backend-cqrs.md`
> 이 문서는 "왜 이 구조를 처음부터 갖추는가" 를 설명하는 상위 원칙이다. (DEC-2026-09-30-01, strata)

## 요약

- **원칙:** 지금 치르는 구조 비용이 이후의 변경 비용을 충분히 상쇄하면, 그 구조는 처음부터 갖춘다. 상쇄하지 못하는 구조는 필요해질 때까지 만들지 않는다.
- **판정 기준은 세 가지다:** 지금 드는 비용, 나중에 그 변경이 필요해졌을 때 드는 비용, 그 변경이 실제로 일어날 가능성.
- **규모에 따라 레이어를 줄이지 않는다.** 레이어 역할과 의존 방향은 모든 규모에서 같다. 규모에 따라 달라지는 것은 도메인 수와 배포 단위뿐이다.
- **모놀리스에서 MSA 로 넘어갈 때 레이어가 거의 바뀌지 않도록 하는 것이 목표다.** 레이어가 덮지 못하는 비용은 데이터 소유, 도메인을 넘는 쓰기, 도메인을 넘는 읽기 세 곳에 몰리므로, 이 세 곳의 규칙도 미리 정해 둔다.
- **선지불한 구조는 집행해야 유지된다.** 컴파일러나 CI 가 막지 않는 경계는 시간이 지나면서 조금씩 새어 나가고, 그만큼 미리 지불한 가치가 사라진다.

## 판정 목록

### 항상 갖추는 구조

| 구조 | 지금 드는 비용 | 상쇄하는 변경 비용 |
|---|---|---|
| 레이어 역할과 한 방향 의존 | 파일 배치와 호출 경로를 규칙에 맞추는 수고 | 기능을 옮기거나 떼어 낼 때 무엇이 함께 딸려 오는지 예측할 수 없게 되는 비용 |
| 명령과 조회를 나눈 서비스 (CQS) | 서비스 파일이 두 배로 늘고 트랜잭션 위치를 의식해야 함 | 읽기 모델을 따로 떼거나 캐시·복제본으로 옮길 때 쓰기 코드까지 뜯어야 하는 비용 |
| 엔티티 모듈과 서비스 모듈을 나눈 빌드 모듈 | 빌드 설정, 모듈 간 의존 선언, 트랜잭션·동기·비동기 처리의 복잡도 | 서비스를 분리할 때 코드 경계를 새로 그어야 하는 비용. 모듈이 그대로 배포 단위 후보가 된다 |
| 외부 시스템 경계의 포트와 어댑터 (DB, 메시징, 외부 API) | 경계마다 인터페이스 하나와 구현 하나 | 외부 시스템 교체, 같은 프로세스 안 호출을 네트워크 호출로 바꾸는 비용 |

### 필요할 때만 갖추는 구조

| 구조 | 갖추는 시점 |
|---|---|
| 이벤트 소싱 (`es-cqrs` 변형) | 감사 추적, 과거 시점 재구성, 이벤트 재생이 요구사항으로 확인됐을 때 |
| 별도 읽기 저장소 | 조회 부하나 조회 모델이 쓰기 모델과 실제로 갈라졌을 때 |

### 갖추지 않는 구조

| 구조 | 이유 |
|---|---|
| 내부 레이어마다 두는 인터페이스 추상화 | 내부 구현을 교체할 일이 거의 없어 상쇄할 변경 비용이 없다. 레이어 방향 규칙만으로 같은 효과를 얻는다 |
| 전면적인 헥사고날 구조 | 포트와 어댑터가 가치를 내는 곳은 외부 경계뿐이다. 내부까지 넓히면 비용만 늘어난다 |

## 레이어가 덮지 못하는 세 경계

모놀리스에서 서비스를 떼어 낼 때 레이어 코드는 거의 그대로 옮겨진다. 남는 비용은 아래 세 곳에서 생긴다. 이 세 곳은 처음부터 규칙으로 정해 둔다.

### 데이터 소유

- 표 하나는 엔티티 모듈 하나가 소유한다. 표의 스키마 변경 이력(changelog)도 그 모듈이 소유한다.
- 다른 모듈은 그 표에 직접 쓰지 않는다. 쓰기는 소유 모듈의 명령 서비스를 거친다.
- 이유: 서비스를 분리할 때 DB 를 나누는 비용은 "누가 어느 표에 쓰는가" 가 흩어져 있을수록 커진다.

### 도메인을 넘는 쓰기

- 두 도메인의 쓰기를 한 트랜잭션으로 묶지 않는다. 한 도메인의 쓰기가 끝난 뒤 이벤트를 발행하고, 다른 도메인은 그 이벤트를 받아 자기 쓰기를 한다.
- 발행 기록은 트랜잭션 안에서 함께 저장한다(outbox 방식, 예: Spring Modulith 이벤트 발행 표). 모놀리스에서는 같은 프로세스 안의 전달로, MSA 에서는 브로커 전달로 바뀌는 지점이 여기 한 곳이 된다.
- 이유: 한 트랜잭션으로 묶인 두 도메인은 서비스로 나누는 순간 분산 트랜잭션 문제가 된다.

### 도메인을 넘는 읽기

- 다른 도메인의 데이터를 읽는 경로는 도메인마다 한 곳으로 정한다. 조회 전용 창구(조회 서비스 또는 조정 레이어), 또는 DB 수준의 외부 표 조회(FDW 등) 가운데 하나를 고르고 섞지 않는다.
- 다른 도메인의 엔티티 타입을 직접 가져다 쓰지 않는다. 조회 결과는 자기 도메인의 타입으로 받는다.
- 이유: 읽기 경로가 한 곳이면, 서비스를 나눌 때 그 한 곳만 네트워크 조회로 바꾸면 된다.

## 규모와 배포 단위

- 작은 프로젝트도 레이어와 모듈 구조는 같다. 도메인이 하나뿐이면 도메인 모듈이 하나일 뿐이다.
- 모놀리스와 MSA 의 차이는 "모듈 몇 개를 한 프로세스로 묶어 배포하는가" 로 본다. 모듈을 다른 프로세스로 옮기는 일은 위 세 경계의 전달 방식을 바꾸는 일이 된다.
- 예산과 운영 여건에 따라 배포 단위는 언제든 합치거나 나눌 수 있다. 레이어와 모듈 경계를 지키는 한, 이 선택은 코드 구조를 다시 짜는 결정이 아니다.

## 언어별 값싼 컴파일 경계

선지불 비용을 가장 낮추는 방법은 언어와 빌드 도구가 이미 제공하는 경계를 쓰는 것이다. 각 언어 바인딩은 "모듈 경계를 무엇으로 만들고, 모듈 안 레이어 방향을 무엇으로 막는가" 를 적는다.

| 언어 | 모듈 경계 (컴파일러 강제) | 모듈 안 레이어 방향 | 순환 |
|---|---|---|---|
| Kotlin / Java | Gradle 멀티모듈 (`implementation` 기본) | ArchUnit (CI 차단) | 모듈 순환은 Gradle 이 거부 |
| Go | 모듈과 `internal/` 패키지 | depguard 등 import 규칙 | 패키지 순환 import 는 컴파일 오류 |
| Rust | cargo workspace 크레이트 | 크레이트 분리 또는 모듈 가시성(`pub(crate)`) | 크레이트 순환은 cargo 가 거부 |
| TypeScript / JavaScript | 워크스페이스 패키지 (`exports` 로 공개 표면 제한) | dependency-cruiser, eslint-plugin-boundaries | 패키지 매니저가 허용하므로 `no-circular` 규칙 필수 |
| Swift | SwiftPM 패키지·타깃 | 타깃 분리 + 검사기 (`profiles/frontend.swiftui/enforcement/`) | 타깃 순환은 SwiftPM 이 거부 |

바인딩 문서는 `profiles/<id>/docs/ko/` 에 있다. 새 언어 바인딩은 실제 프로젝트가 생길 때 추가한다.

## 선지불의 보존

- 모듈 경계는 빌드 도구가, 모듈 안 레이어 방향은 CI 의 아키텍처 테스트가 막는다. 편집 시점의 훅은 빠른 피드백일 뿐 정본 판정이 아니다.
- 기존 코드에 위반이 쌓여 있으면 기준선으로 묶어 두고, 새로 생기는 위반만 막는다. 기준선은 줄어드는 방향으로만 갱신한다.

## 근거 사례 (한 백엔드 프로젝트, 2026-09)

- 주문 모듈의 3.0 설계를 결제(billing) 모듈로 옮길 때, 작업은 엔티티·문서·서비스 모듈을 새로 만들고 게이트웨이 경로를 돌리는 것으로 끝났다. 레이어 규칙과 서비스 코드의 모양은 바뀌지 않았다 (그 프로젝트의 2026-09-08 결정).
- 실제로 고민한 비용은 같은 DB 에 두 모듈을 공존시키는 장치와 데이터 이동이었다. 이 경험이 "데이터 소유" 경계를 규칙으로 올린 근거다.
- 2026-07 ArchUnit 실측에서 모듈 안 레이어 위반이 1,500건 가까이 나왔다. 모듈 경계는 컴파일러가 지켰지만 모듈 안 경계는 경고에만 의존했기 때문이다. "선지불의 보존" 절의 근거다.
