# 结构预付原则

> 正本：strata-kit `core/docs/zh/architecture/prepaid-structure.md` — 从 strata `docs/03-architecture/prepaid-structure.md` 迁移而来（订单 2026.10.29-06，2026-10-29）。规则 YAML 在 `core/rules/`。

> 层规则的机器可读正本：`core/rules/layer-rules.yaml` / 各层说明：`core/docs/zh/architecture/backend-cqrs.md`
> 本文是解释“为什么从一开始就备齐这套结构”的上层原则。（DEC-2026-09-30-01，strata）

## 摘要

- **原则：**如果现在付出的结构成本足以抵消以后的变更成本，就从一开始备齐该结构。无法抵消的结构，在需要之前不构建。
- **判定标准有三个：**现在的成本、以后该变更变得必要时的成本、该变更实际发生的可能性。
- **不因规模而削减层。**层的职责和依赖方向在所有规模下都相同。随规模变化的只有领域数量和部署单元。
- **目标是在从单体迁移到 MSA 时，层几乎不发生变化。**层无法覆盖的成本集中在数据所有权、跨领域写入、跨领域读取三处，所以这三处的规则也要预先确定。
- **预付的结构只有靠强制执行才能维持。**编译器或 CI 不拦截的边界会随时间一点点泄漏，预先付出的价值也随之消失。

## 判定清单

### 始终备齐的结构

| 结构 | 现在的成本 | 所抵消的变更成本 |
|---|---|---|
| 层的职责与单向依赖 | 让文件布局和调用路径符合规则的功夫 | 迁移或拆出某个功能时，无法预测会连带哪些内容的成本 |
| 拆分命令与查询的服务（CQS） | 服务文件增加一倍，并且必须留意事务所在位置 | 单独拆出读取模型，或迁移到缓存、副本时，连写入代码也要拆开的成本 |
| 按实体模块与服务模块拆分的构建模块 | 构建配置、模块间依赖声明，以及事务、同步与异步处理的复杂度 | 拆分服务时需要重新划定代码边界的成本。模块本身就成为部署单元的候选 |
| 外部系统边界的端口与适配器（DB、消息、外部 API） | 每个边界一个接口和一个实现 | 更换外部系统，或把进程内调用改为网络调用的成本 |

### 仅在需要时才备齐的结构

| 结构 | 备齐的时机 |
|---|---|
| 事件溯源（`es-cqrs` 变体） | 审计追踪、重建过去时间点、事件重放被确认为需求时 |
| 独立的读取存储 | 查询负载或查询模型与写入模型实际上已经分叉时 |

### 不备齐的结构

| 结构 | 原因 |
|---|---|
| 在每个内部层设置的接口抽象 | 几乎不会替换内部实现，没有可抵消的变更成本。仅靠层方向规则就能获得同样的效果 |
| 全面的六边形架构 | 端口与适配器只在外部边界产生价值。扩展到内部只会增加成本 |

## 层无法覆盖的三个边界

从单体拆出服务时，层代码几乎原样迁移。剩下的成本产生在下面三处。这三处从一开始就用规则确定。

### 数据所有权

- 一张表由一个实体模块所有。表的 schema 变更历史（changelog）也由该模块所有。
- 其他模块不直接写该表。写入要经过所有者模块的命令服务。
- 原因：拆分服务时拆分 DB 的成本，会随着“谁写哪张表”越分散而越大。

### 跨领域写入

- 不把两个领域的写入绑在一个事务中。一个领域的写入完成后发布事件，另一个领域接收该事件并执行自己的写入。
- 发布记录在事务内一并保存（outbox 方式，例如 Spring Modulith 的事件发布表）。这样，在单体中为进程内传递、在 MSA 中变为代理传递的切换点，就只有这一处。
- 原因：绑在一个事务里的两个领域，一旦拆成服务就会变成分布式事务问题。

### 跨领域读取

- 读取其他领域数据的路径，每个领域固定为一处。在只读窗口（查询服务或协调层）和 DB 级的外部表查询（FDW 等）中选择一种，不要混用。
- 不直接引用其他领域的实体类型。查询结果用自己领域的类型接收。
- 原因：读取路径只有一处，拆分服务时只需把这一处改为网络查询即可。

## 规模与部署单元

- 小项目的层与模块结构也相同。只有一个领域时，只是只有一个领域模块而已。
- 单体与 MSA 的区别，看的是“把多少个模块打包进一个进程来部署”。把模块迁到另一个进程，就等于改变上述三个边界的传递方式。
- 根据预算和运维条件，部署单元可以随时合并或拆分。只要守住层和模块边界，这个选择就不是重写代码结构的决定。

## 各语言廉价的编译期边界

降低预付成本最有效的方法，是使用语言和构建工具已经提供的边界。每种语言的绑定要写明“用什么构建模块边界，用什么拦截模块内的层方向”。

| 语言 | 模块边界（编译器强制） | 模块内的层方向 | 循环 |
|---|---|---|---|
| Kotlin / Java | Gradle 多模块（默认 `implementation`） | ArchUnit（CI 拦截） | 模块循环由 Gradle 拒绝 |
| Go | 模块与 `internal/` 包 | depguard 等 import 规则 | 包的循环 import 是编译错误 |
| Rust | cargo workspace crate | crate 拆分或模块可见性（`pub(crate)`） | crate 循环由 cargo 拒绝 |
| TypeScript / JavaScript | 工作区包（用 `exports` 限制公开面） | dependency-cruiser、eslint-plugin-boundaries | 包管理器允许循环，所以必须有 `no-circular` 规则 |
| Swift | SwiftPM 包与 target | target 拆分 + 检查器（`profiles/frontend.swiftui/enforcement/`） | target 循环由 SwiftPM 拒绝 |

绑定文档在 `profiles/<id>/docs/zh/` 中。新的语言绑定在出现真实项目时再添加。

## 在前端应用同一原则的例子

- 令牌三级（原始值 → 别名 → 组件）预付了别名层，把更换主题或品牌的成本降低为一处别名定义。详情：`core/docs/zh/architecture/frontend-design-contract.md`
- 组件层级只能自上而下地引用。详情：`core/docs/zh/architecture/frontend-web.md`

## 预付的保全

- 模块边界由构建工具拦截，模块内的层方向由 CI 的架构测试拦截。编辑时的钩子只是快速反馈，不是正本判定。
- 若既有代码中已积累了违规，就把它们固定为基线，只拦截新产生的违规。基线只朝减少的方向更新。

## 依据案例（某个后端项目，2026-09）

- 把订单模块的 3.0 设计迁移到计费（billing）模块时，工作以新建实体、文档、服务模块并跑通网关路径而告终。层规则和服务代码的形态没有变化（该项目 2026-09-08 的决定）。
- 真正费心的成本是让两个模块在同一个 DB 中共存的机制，以及数据迁移。这一经验是把“数据所有权”边界提升为规则的依据。
- 2026-07 的 ArchUnit 实测中，出现了近 1,500 条模块内的层违规。模块边界由编译器守住了，但模块内的边界只依赖警告。这是“预付的保全”一节的依据。
