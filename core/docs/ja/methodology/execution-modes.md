# 実行モード (Execution Modes)

> 正本: strata-kit `core/docs/ja/methodology/execution-modes.md` (2026-10-29 strata `docs/04-agents/execution-modes.md` から移管、DEC-2026-10-29-11)。

> Strata 方法論の二重の実行モードを定義します。
> すべてのセッションは開始時に実行モードを明示的に宣言しなければなりません。

## 原則

- **デフォルトは Task Mode** — 宣言しなければ Task Mode とみなす
- **Verbal Mode は意図的な例外** — 明示的に選んだ場合にのみ使える
- **モード切り替えは一方向** — Verbal → Task は可、Task → Verbal は禁止

> **作業モードとの対応 (2026-10-29、DEC-2026-10-29-15・19)**: 入口スキル (using-strata の 4 段階目) の四つの作業モードは、この二つのモードを分けたものである。Verbal = 読み取り専用 (調査・質問・レビュー) + タスクファイルなしで終わる単一セッションの変更、Task = 複数セッション (オーダーのある作業) + オーケストレーション (複数のセッション・役割が並行)。セッションが負う義務 (アクティブファイル・ハンドオフ・オーダー) は作業モードが決め、下の定量基準は Verbal で終えられるかを判断するのに使う。
- **状態を変更する前に要約・確認** — ファイル修正、セッションへの注入、外部 CLI 呼び出し、コミット/デプロイのように元に戻しにくい、または観測可能な状態を変える作業は、進める内容の要約をまず提示し、ユーザーの確認を得てから実行する

## モード定義

### Task Mode (デフォルト)

Builder が `_order.yaml` + `task-{nn}.yaml` の仕様を書き、Worker がその仕様に基づいて実行するモード。

**適用時点:**
- スプリント単位の実行計画
- マルチセッションでの機能実装
- 3 ファイル以上の変更
- 2 レイヤー以上への影響
- 新しいアーキテクチャパターンの確立

**義務事項:**
- `_order.yaml` を書く (作業指示書)
- 個別の `task-{nn}.yaml` を書く (Worker 実行仕様)
- TASK_TRACKER.md を更新する
- ハンドオフ文書を書く
- アーキテクチャ決定があれば KB に還流する

### Verbal Mode (例外)

Builder が直接実行する、または口頭の指示で素早く処理するモード。

**適用箇所:**
- アイデア出し、探索、設計レビュー
- 単一ファイルの修正
- バグのホットフィックス (緊急)
- 文書修正、設定変更
- 10 ターン以内に終えられる作業

**義務事項:**
- タスク仕様は不要
- TASK_TRACKER の更新は不要
- ハンドオフは任意 (決定事項があれば記録)
- **決定が発生したときの decision レコード記録 (decision writer CLI) は免除できない** (モードを問わない絶対規則 — `decisions.yaml` は生成インデックスであり、手で編集してはならない)

## モード選択基準 (定量)

```
IF (修正ファイル ≤ 3) AND (影響レイヤー ≤ 1) AND (想定ターン ≤ 10)
   AND (新ドメイン = 0) AND (探索段階 ≤ 1):
    → Verbal Mode 許可
ELSE:
    → Task Mode 強制
```

| 指標         | Verbal 許可 | Task 強制 |
| ------------ | ----------- | --------- |
| 修正ファイル | ≤ 3         | 4+        |
| 影響レイヤー | 1           | 2+        |
| 想定ターン   | ≤ 10        | 11+       |
| 新ドメイン   | 0           | 1+        |
| 探索段階     | ≤ 1         | 2+        |

**すべての条件が Verbal の範囲内にあるときにのみ Verbal を許可する。ひとつでも超えたら Task を強制する。**

## モード宣言

セッション開始時に、このセッションのファイル `.strata/local/active/{session}.yaml` にモードを記録し、ハーネスのセッション ID (Claude Code では `CLAUDE_CODE_SESSION_ID`) を `harness_session_id` に書く — 開始ヘッダーとコンパクション後の復元は、このフィールドかファイル名でこのセッションのファイルを見つける:

```yaml
harness_session_id: "9496c8b3-…"   # CLAUDE_CODE_SESSION_ID
session:
  date: "2026-04-23"
  mode: "verbal"              # verbal | task
  declared_scope: "デバウンス設計の検討とブリーフィング"
  escalation_threshold: 3     # このファイル数を超えたら task mode へ切り替え
  order_ref: null              # task mode のときは _order.yaml のパス
```

## モード切り替え (Verbal → Task)

Verbal で始めたがスコープが大きくなった場合:

1. Builder の 5 ターン自己診断で検知する (ファイル数・レイヤー数を確認)
2. ユーザーに「Task Mode への切り替えが必要」と報告する
3. `_order.yaml` を書く — `escalated_from: "verbal"` フィールドを含める
4. すでに完了した作業は `_order.yaml` の `completed_before_spec` セクションに記録する
5. 以降の作業はタスク仕様に基づいて進める

```yaml
# _order.yaml (切り替え時)
order:
  id: "2026.04.23-01"
  title: "デバウンス MongoDB 同期"
  escalated_from: "verbal"
  completed_before_spec:
    - "CacheGenericOperator に SET 演算を追加 (verbal 段階で完了)"
  tasks:
    - id: "task-01"
      title: "DirtyMarkService を実装"
      # ... 以降のタスクは通常の仕様
```

## モデル割り当て戦略

Worker タスクには、実行する**推論等級 (reasoning tier)** を明示します。具体的なモデル名ではなく等級を書き、等級→モデルの対応づけはツールアダプターが担います (ツール中立)。

### 推論等級ごとの割り当て基準

| 等級 | 割り当て基準 | 相対コスト | 代表的な作業 |
|------|--------------|------------|--------------|
| **deep** (高推論) | 新規パターンの確立、クロスレイヤー推論、複雑なリファクタリング | 高 | アーキテクチャ設計 + 実装、新規システム |
| **standard** (標準) | 既存パターンの踏襲、単一レイヤーの CRUD、テスト、文書化 | 低 | REST Docs、QueryService の追加、KB 文書 |
| **light** (軽量) | 文書検索、規則の参照、単純な要約 | 最低 | KB 検索、ハンドオフ要約 |

> **等級→モデルの対応づけは Core ではなくツールアダプターの責任である。** (アダプターの例 — Claude: `deep→Opus`、`standard→Sonnet`、`light→Haiku`。この対応づけはアダプターの文脈であり、Core の規則ではない。)

### モデル選択の判断ツリー

```
タスクは既存パターンを踏襲するか?
  ├─ YES → 参照実装は明確か?
  │         ├─ YES → standard
  │         └─ NO  → deep (パターンの解釈が必要)
  └─ NO  → 新しいアーキテクチャ判断が必要か?
            ├─ YES → deep
            └─ NO  → standard (単純な新規コード)
```

### タスク仕様での等級表記

```yaml
execution:
  model_tier: "standard"
  model_reason: "既存の REST Docs パターンを踏襲、新たな判断は不要"
```

`model_reason` は必須です。Builder がモデル選択の根拠を明示することで、次のセッションでも同じ基準を適用できます。

## エージェント別の既定推論等級

| エージェント | 既定の等級 | 変更可否 |
|--------------|------------|----------|
| Builder | deep | 不可 (オーケストレーションは常に高水準の推論が必要) |
| Worker | タスクごとに指定 | 可 (deep または standard) |
| Supporter | light/standard | 可 (検索は light、要約は standard) |

> 具体的なモデルはツールアダプターが等級に対応づける (上の「等級→モデルの対応づけ」の注記を参照)。Core は等級だけを規定する。

## 検証軸 (Verification Tier)

検証軸は実行モードと直交する。実行モードが*どう作業するか*なら、検証軸は*結果を誰が検証するか*を扱う。
enum 値は `solo | self_verified | cross_verified` である。
定義、既定値、Core の正本 (SoT) を変更するときに `cross_verified` が必須となる範囲は、`core/docs/ja/methodology/verification-tier.md` が source of truth である。
Cross-Verified の検討は `skills/strata.review/SKILL.md`（レビューパケットを新しいコンテキストのレビュアーに一度送る）で行う。

## 方法論フィードバックループ (Methodology Feedback Loop)

Worker/Reviewer が見つけた方法論の隙間は `methodology_signals` で報告し、Builder が backlog に積んで昇格させる。
フローと Promotion Gate は、`core/docs/ja/methodology/task-spec-schema.md` の「Promotion Gate」節が source of truth である。
`methodology_signals` と `methodology-backlog.yaml` のフィールドスキーマは `core/docs/ja/methodology/task-spec-schema.md` が定義する。

## 運用軸 (Agent Operations)

実行モード・検証軸の上に、エージェントを**多数・長時間**動かすときの運用規律は別の軸として扱う:
マルチセッション (hub-and-spoke)、夜間バッチ (budgeted batch)、Decision Inbox、自己申告の検証ゲート。
→ `core/docs/ja/methodology/agent-operations.md` (この文書は参照のみで、規則の定義はそちらにある)

## 絶対規則 (モード不問)

> **正本はこの節ではない** (DEC-2026-10-29-19)。どの規則がこのプロジェクトに適用されるかは、憲法 (`core/constitution/constitution.yaml` の条項) とプロジェクトが採用したカード (ウィザードが書いた `.strata/kit/registry.yaml` の `must_cards`) が決め、生成された指示 (AGENTS.md) がその集合を載せる。規則の文言の正本は `core/cards/` のカードである。
> この節は、それらのカードの元になった原文と根拠 (事故・理由) を残したものである。憲法 1.2.0 からは 5・7 は条項ではなく、プロジェクトが採用したときにだけ適用される採用型 must である。規則を変えるときはカードと憲法を直し (決定レコード)、この節は直さない。

原文 (2026-09-30、DEC-2026-09-30-02 当時すべてのセッションに適用していた一覧):

1. **状態を変更する前に、進める内容の要約を提示してユーザーの確認を得る**
   - 対象: ファイル修正、セッションファイル/リレーの注入、外部 CLI 呼び出し、コミット/デプロイ/削除、長時間実行の作業、コスト・権限・データに影響する作業
   - 要約には、目的、実行する作業、変更/影響の範囲、検証方法、巻き戻し/中断の条件を含める
   - 単なる参照・検索・ファイル読み取りのように状態を変えない調査は例外として許可する
   - **semantic vs mechanical**: 意味・規則・契約を変える semantic な変更は承認が必須。意味を変えない mechanical な変更 (誤字・リンク・書式) は、**static に証明できる場合にのみ**自動許可の候補となる。曖昧なら承認の側に置く。LLM 自身の「mechanical」判断を自動許可の根拠にしない
2. **アーキテクチャ決定が発生したら decision レコードを即座に記録する** (decision writer CLI — インデックスと vault の DEC ノートは自動で再生成される)
3. **レイヤー違反の禁止** — ハーネスが止める強さはプロジェクトの執行等級が決める (DEC-2026-10-29-17)。エージェントは等級に関係なく新しい違反を書かない
4. **命名規約の遵守** — Hook が警告する
5. **Soft Delete のみを使う** — 採用型 (憲法 1.2.0、DEC-2026-10-29-14): ストレージのあるプロジェクトが採用したときに適用
6. **セッション状態・進行中の作業・ハンドオフは、会話コンテキストではなくファイルに残す** — 状態を変えるセッションに適用し、読み取り専用のセッションには残す状態がない (DEC-2026-10-29-15) — セッションが中断するときは このセッションの `.strata/local/active/{session}.yaml` (単一ファイル `active-task.yaml` は、セッション別ファイルがないときだけ読む以前の形式) に現在の状態を記録し、ハンドオフと作業履歴は vault に置く
7. **作業ツリー (git worktree) はユーザーの同意があるときにのみ作る** (DEC-2026-09-17-01) — 採用型 (憲法 1.2.0): ユーザーの既定の採用一覧にあるか、プロジェクトが採用したときに適用
   - 自動モードでも同じである。ツールアダプターの作業ツリー分離 (例: Claude Code の Agent ツール `isolation: "worktree"`、`EnterWorktree`) と `git worktree add` のいずれも該当する
   - 既定は、ユーザーが見ているチェックアウトの単一ブランチで順番に作業することである。Worker を複数使う場合も、同じチェックアウトで順番に実行する
   - 並列セッション・並列 Worker のために作業ツリーが本当に必要なときにのみ、必要性、ブランチ名、後片付けの計画を一項目にまとめて提案し、受け入れられた場合にのみ作る。一度の受け入れはその提案にのみ有効である
   - 同意を得て作った作業ツリーは、タスクが終わったらブランチを残して片付け、場所とブランチを報告する
   - 理由: 作業ツリーで分離すると、エージェントが書いた内容のレビュー・検討が正常に機能せず、ユーザーが変更と作業履歴を直接確認できず、形状の追跡が難しくなる
8. **推測を確かめるためのデプロイは、デプロイでしか再現できない環境に限る** (DEC-2026-09-18-01、strata)
   - コードの読解・ログ・単体テスト・ローカル実行で確かめられる推測は、デプロイで確かめない。共有環境 (dev・stage) に載せるのは、その環境でしか再現しない現象 (インフラ・ルーティング・他サービスとの連携・実データ) を確かめるときだけである
   - デプロイの前に、何を確かめようとしているのかを、確定した事実と推測に分けて書き、元に戻す方法 (revert コミット・以前のイメージ) も併せて報告する
   - 認証・ルーティング・セッションのように、他のラインや他のユーザーに影響が及ぶ変更は、そのラインのユーザーフロー (例: 2.0 ログインと 3.0 ログインの両方) で実測した後にのみ載せる
   - 理由: 2026-09-18 に stage で推測だけでゲートウェイのルートを昇格させたところ 2.0 ログインが壊れ、推測を直して再び載せるデプロイが一日に何度も繰り返された。デプロイは元に戻すのにも時間がかかり、他の人の作業を止める
9. **ハンドオフの未決 (pending) 項目には、塞がっている理由 (blocker) と解ける条件 (unblocked_by) を併せて書く**
   - 「待機」だけを書くことは禁止する。次のセッションが何を待っているのか分からなければ、未決は繰り越されるだけになる
