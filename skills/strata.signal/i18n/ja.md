# strata.signal

## 概要

運用の段階は指標を示します。製品の流れを代わりに引き受けることはしません。指標は二種類あります。strata 自体の計測（kit のリビジョン、セッション、検証、ハンドオフ、git）と、プロジェクトがすでに持っている流れ — QA 台帳、カバレッジのテストケース — から読むだけで得た製品フローの指標です。どちらかが悪化したら、このスキルはそれを根拠とともにノート一枚に残し、選ぶことを本人に渡します。その変化が何につながりうるかと理由を示し、本人が選んだものを記録します。

## 使う場面

librarian の日次レポートに新しい未処理の信号があるとき、検査が長く開いたままの信号を示したとき、本人が悪化した指標を見て残しておきたいときに使います。製品の障害、アラート、ユーザーのフィードバックには使いません — それは製品自身の機能の仕事です。規則を決めること（strata.decision）にも使いません。ノートを書くと、読み取り専用のセッションは単一セッションへ上がります。

## 手順

1. **変化を見つける。** `python3 -m kb signals candidates --project <p>` で候補を示し、`python3 -m kb indicators show --project <p>` で製品フローの指標を前回の収集と比べて示します。本人が同意したら `--write` で書きます（librarian の日次作業は行き先なしで自ら書きます）。証拠：候補の一覧またはノートのパス。
2. **根拠を確かめる。** どのノートも根拠の節に計測値とその基準 — 前のリビジョンまたは前回の収集、そしてしきい値 — があります。候補の拠り所が少なすぎる（セッション一つ、収集一回）なら、ノートにそう書きます。証拠：ノートの根拠の節。
3. **行き先の候補を示して尋ねる。** 未処理の信号ごとに、候補とそれぞれ一行の理由を示します。方法論のバックログ項目（仕事の進め方や kit の空白）、アイデアノート（育てる価値はあるがまだはっきりしない、ideation.shape）、企画文書（計画する仕事、strata.planning）、決定（規則を定めることになるなら strata.decision）、破棄（ノイズ、すでに対応済み）。製品自身の流れを改善することも、ほかの仕事と同じ計画された仕事です — このスキルがその流れに書き込むのではなく、本人の選択から始まります。自分では選びません。証拠：候補と問い。
4. **受け取り側を作り、選択を記録する。** 受け取り側は本人が承認した文面でのみ書きます。バックログ項目は追加する前に見せ、アイデアは ideation.shape へ、企画は strata.planning へ渡します。そのあと `python3 -m kb signals route --project <p> <ノート> --to <項目 id または vault のパス> --by <本人>` を実行します。破棄なら `--drop "<理由>" --by <本人>` です。コマンドはまだ存在しない対象を拒否します。証拠：route の出力。
5. **ノートを検査する。** `python3 -m kb signals check --project <p>` を実行します。示された問題はすべて直します。14日を超えて開いている信号は、エージェントが決めずに問いとして本人に示します。証拠：コマンドの出力と終了コード。

## 言い訳

| 考え | 反論 |
|---|---|
| 「傾向は明らかなので、バックログ項目を直接追加しよう。」 | それでは誰も選んでおらず、次に読む人はそれがどこから来たのか分かりません。信号を書き、候補を示し、本人に選んでもらいます。 |
| 「本人は忙しいので、いちばんありそうな行き先を自分で選ぼう。」 | 行き先は本人のものです（DEC-2026-11-01-17）。開いたままにして尋ねます。開いた信号にコストはかかりませんが、誤った項目は片付けのコストがかかります。 |
| 「QA の指標が悪化したので、欠陥を登録するか台帳を直そう。」 | QA 台帳と欠陥ストアは製品自身の流れです。kit は読むだけで、変えることは本人が選ぶ計画された仕事です。 |
| 「この障害報告は重要なので、信号としても残そう。」 | 障害とフィードバックには製品の機能の中に居場所があります。ここに二つ目の写しを置くと記録が分かれます。 |

## 危険信号

- 本人の承認なしに信号から作られたバックログ項目、アイデアノート、決定。
- decided_by がエージェントや librarian になっている routed のノート。
- 根拠に比較基準のないノート。
- このスキルから製品自身の流れ（台帳、欠陥ストア、カバレッジレポート）に書き込んだこと。

## 検証

- 新しいノートはどれも projects/<p>/signals/ にあり、根拠に値とその基準がある。
- routed のノートはどれも選んだ人の名前があり、対象が存在する。
- 製品自身の流れに何も書き込んでいない。
- `python3 -m kb signals check --project <p>` が 0 で終わり、長く開いた信号は本人に尋ねた。
