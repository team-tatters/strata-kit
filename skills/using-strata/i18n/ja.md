# using-strata

## 概要

`using-strata` は入口のスキルです。やることは二つだけです。セッションが今どこにあるかを出力して、ユーザーとエージェントが同じ事実を共有できるようにすること、そして作業をそれを担当するスキルへ振り分けることです。作業そのものは行いません。このファイル自体も変わりません。拡張は、このファイルではなく、重ねて読むレジストリから来ます。

## 使う場面

- すべてのセッションの開始時。確認の質問、コードベースの検索、ファイルの読み取りを含め、どんな応答よりも先に使います。質問も作業です。
- 作業の形が変わるたびに。機能開発の途中で入ったバグ報告、デプロイの依頼、ドキュメント更新の依頼などです。
- 特定の作業を一つ実行するためにサブエージェントとして派遣された場合は使いません。その場合は受け取った作業に従い、このスキルは無視します。

## 手順

1. **プロジェクトのマニフェストを読みます。** プロジェクトルートの `.strata/profile.yaml` を開きます。なければ止まって `strata.init-wizard` を呼び出します。証拠: マニフェストのパスと `project` の値。
2. **ヘッダーがないときだけ、レジストリを層ごとに読み込みます。** 開始フックが strata ヘッダーを出力していれば、そのヘッダーが有効な must カードとレジストリの層ごとの状態をすでに示しています。それを使い、憲法とレジストリの全文を開き直しません。手順 5 のルートの対応づけはハーネスが示すスキルの説明で行い、ヘッダーに独自のルートを持つプロファイル層・プロジェクト層が見えるときだけ、そのレジストリファイルを開きます。ヘッダーがなければ、次を行います。strata-kit の `skills/registry.yaml`、次にプロファイルのレジストリ、次にプロジェクトのレジストリ(ウィザードが書いた `.strata/kit/registry.yaml` と、スキルパックがあれば Tier P の `skills/registry.yaml`)を読みます。各ファイルを開き、ある層のファイルが存在しない場合は、飛ばさずにその層は「なし」と述べます。後の層はルートを追加し、同じ `skill` のものは先の層を上書きします。このスキルの `required_context` にあるファイル(憲法)も、要約に頼らず自分で開きます。証拠: ルートの一覧とそれぞれの出どころの層、および開いた required_context のパス。 ユーザー層（`~/.strata/skills`: kit のパックは `packs/`、人が作ったスキルは `local/`）は、プロファイルの後、プロジェクトの前に読みます。ユーザー層はルートを足すだけです。他の層に同じ名前があれば拒否され、例外は `overrides:` で置き換えるコアスキルを書いた local スキルだけで、ヘッダーがそれを示します（`python3 -m kb skills check`、DEC-2026-10-31-36）。
3. **コンテキストヘッダーを出力します。** ドメイン(業務または個人)、プロジェクト ID と別名、プロファイル ID、有効な must カード(ID のみ)、免除された should カードとその理由、最新のハンドオフまたは active-task ファイルにある次のアクション。開始フックがヘッダーを出力していれば、そのヘッダーをもう一度示し、作業モードを加えます。ファイルから組み立て直しません。アクティブファイルもハンドオフも読めないとき(変数未設定・ツール拒否・ファイルなし)は、そう伝え、作業の状況を尋ねる前にリポジトリ自体の痕跡 — NOTES・HANDOFF のようなノートファイル、`git log`、ブランチ — を読みます。ヘッダーがどこを探したかを示します。証拠: 返信の最初に置いたヘッダー。
4. **作業モードを決めます。** ハーネスが決めていればそれを使います(Quilt の piece は指示文にモードを書きます)。そうでなければ選びます: 読み取り専用(調査・質問・レビュー。ファイルや外部の状態を変えない)、単一セッション(このセッションで終わる変更)、複数セッション(セッションをまたぐ作業。オーダーがある、または生まれる)、オーケストレーション(複数のセッション・役割が並行して働く)。義務: 読み取り専用はヘッダーとルート決定のみで、アクティブファイルとハンドオフはありません。単一セッションは `mode` と `harness_session_id` (ハーネスのセッション ID。Claude Code では `CLAUDE_CODE_SESSION_ID`。ヘッダーとコンパクション後の復元がこのセッションのファイルを見つける手がかり) を書いたアクティブファイル、検証の証拠、決定の記録、保留が残るときだけハンドオフ。複数セッションはこれに加えてオーダーとセッションごとのハンドオフ。オーケストレーションはさらに役割ごとの権限ポリシー、タスクファイルに注入した制約、レビューパケット。読み取り専用のセッションが状態を変えようとするときは、先に単一セッションへ上がります。決定の記録と状態変更前の確認はすべてのモードに適用されます。証拠: ヘッダーのモード。
5. **作業をルートに対応づけます。** 依頼を、要求されたロケールのトリガーと照らし合わせ、なければ `en` にフォールバックします。当てはまりそうなルートがあれば、その名前を挙げます。複数当てはまる場合は、プロセススキル(`strata.spec`、`strata.order`)を実装スキル(`strata.build-task`)より先にします。証拠: ルートと一行の理由。
6. **スキルを呼び出します。** 「<理由>のため <スキル> を使います」と宣言し、そのとおりに従います。そのスキルのチェックリストの項目ごとに todo を作ります。読んでみて合わなければ、そう述べて手順 5 に戻ります。

## 言い訳と反論

| 考え | 反論 |
|---|---|
| 「ただの簡単な質問だから。」 | 質問も作業です。ヘッダーを出力してルートを決めてください。読み取り一回で済みます。 |
| 「スキルを確認する前に、もっと文脈が必要だ。」 | スキルの確認は文脈の収集より先です。どんな文脈を集めるかはスキルが教えてくれます。 |
| 「このスキルの内容は覚えている。」 | スキルはコアのリビジョンとともに変わります。現行版を読んでください。 |
| 「この変更にスキルは大げさだ。」 | 小さな変更は大きな変更になります。ルーティングは安く、チェックポイントを飛ばすことは高くつきます。 |
| 「読み取り専用だから、ヘッダーは省いてよい。」 | 読み取り専用が省くのはファイルであって、ヘッダーではありません。must カードを示すのがヘッダーです。 |
| 「ユーザーが急いでいる。」 | ヘッダーは五行です。誤ったルートはそれより多くの時間を使います。 |

## 警告サイン

- コンテキストヘッダーなしに、答えや行動から始まる返信。
- スキル名も理由も示さずに進む作業。
- `.strata/profile.yaml` のないプロジェクトでファイルを編集するセッション。
- ヘッダーに載せた must カードを、後続の手順が理屈をつけて回避すること。
- 単一セッションに上がらずにファイルを編集する読み取り専用のセッション。

## 検証

ルーティングしたスキルに進む前に、次のすべてを確認し、一行で述べます。

- ヘッダーを最初に出力し、そこにプロジェクト ID とプロファイルが書かれている。
- レジストリの層を読んだか開始フックのヘッダーが示しており、ルート(または「なし、理由は …」)を述べた。
- 作業モードを述べた。
- ルーティング先のスキルの `required_context` の一覧を読み込んだ。
