# strata.security

## 概述

核心每天给运维者一页笔记：什么是新出现的，什么仍然开放，什么已关闭，哪些对象没有人在看。这个技能是那页笔记的人这一侧。它读取每日作业写下的内容，把人的判断写回文件（工单、已接受的风险、阈值、链接），并在人带来新的实测值时重建对象清单。它不自行采集、评级或打补丁——采集与评级由每日作业按记录的规则完成，打补丁只在条件成立时通过 `patch plan`·`patch run` 进行。

## 何时使用

读笔记是每日触发点。需要新增监视对象（服务器、桌面、依赖文件）、有人问某个漏洞是否影响我们、或要设定阈值或已接受的风险时也使用。不用于事故响应（operator 的流程），也不用于产品自身的缺陷库。

## 流程

1. **读当天的笔记。** 打开 `security/notes/<day>.md`。先看紧急行，再看带首次出现日的未处理项，再看无眼对象。若开头写有未能查看的层，先说这件事。证据：笔记路径与 counts 行。
2. **判断前先顺着链接走。** 对每个要处理的项，打开 `security/matches/<day>.yaml` 中的记录与匹配：以哪个标识符匹配、哪个范围、分数多少以及来自哪个来源（NVD、CNA、厂商）、是否由其他来源补入。证据：记录 id 与匹配 id。
3. **与人一起分类。** 紧急项已有工单（每日作业生成，默认归属 infra）——展示工单，只问归属（`assign`）。对建议项提问：升为工单（`promote <match> --by`）、写明理由与期限接受为风险（`accept ... --until --by`）、或留在笔记中。不要独自决定。证据：命令输出。
4. **给无眼对象以眼睛。** 对每个无眼对象询问其公告位置（GitHub 仓库、厂商页面），写入 `security/sources.yaml` 的手动链接；没有锁文件的仓库，说明所需的 SBOM。证据：manual_links 行。
5. **用实测值重建清单，绝不从服务器获取。** 当人粘贴 `docker ps`、compose、`dpkg-query` 输出或 OS 版本时，只保留镜像、版本和包名（去掉环境变量、密码、哈希），放到 `security/registry.yaml` 指向的位置，运行 `python3 -m kb security inventory --project <p> --env <e> --write` 并展示差异。证据：差异输出。
6. **阈值只通过命令修改。** `python3 -m kb security grading set --project <p> [--env <e>] threshold <值> --by <人>` —— history 行就是记录。证据：history 条目。
7. **只在条件成立时打补丁。** `patch plan <order>` 给出条件（代码层面、无停机、数分钟内替换、已记录的接受）。`patch run` 无条件则拒绝；需要接受的执行必须先在工单中记录人的接受。证据：工单中的计划与执行记录。

## 合理化

| 想法 | 反驳 |
|---|---|
| “标题是远程代码执行，标为紧急吧。” | 评级来自分数与记录的阈值。没有分数就是 no-score 的建议——展示，不要上调。 |
| “KEV 列出了它，所以一定紧急。” | KEV 只决定笔记排序，从不评级（DEC-02）。低于阈值即为建议。 |
| “我 ssh 进去自己确认版本。” | 代理不进入服务器。向人索取命令输出。 |
| “compose 文件里有版本，原样保存。” | 里面也有密码。只留镜像与版本，说明去掉了什么。 |
| “人很忙，我先接受这个风险。” | 已接受的风险属于人，带理由与期限。留在笔记里。 |

## 红旗

- 在文件中手改的评级或阈值。
- 没有期限或由代理记录的已接受风险。
- 从会话中执行的服务器命令。
- 带密钥的 compose 或环境文件被复制进 vault。
- 仅凭名字把无眼对象匹配到 CVE。

## 验证

- 每个动作都指向当天笔记的一行或一个匹配 id。
- 清单变更后 `python3 -m kb security inventory --all` 退出码为 0。
- grading.yaml 的 history 只增加了实际变更；accepted-risks.yaml 每行都有 reason、until、by。
- 未触碰服务器或产品自身的流程。
