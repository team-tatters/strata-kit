# 작업 흐름 — 아이디어에서 운영까지, 그리고 다시

> 정본: strata-kit `core/docs/en/methodology/work-flow.md` (2026-11-01, MB-strata-kit-2026-019, DEC-2026-11-01-03).

> 전체 흐름을 한 장에 적는다. 단계마다 무엇이 들어오고 무엇이 남는지, 언제 다음 단계를 시작할 수 있는지, 누가 하는지, kit 의 어디에 있는지. kit 은 순서를 강제하지 않는다. 스킬이 끝나면 이어질 수 있는 것을 제안하고(`python3 -m kb skills next <스킬>`), "아무것도 안 함"이 늘 목록에 있으며, 고르는 것은 사용자다. 프로젝트의 `standing: {<영역>: decides|proposes}` 는 제안의 순서와 문구만 바꾸고, 허용되는 것은 바꾸지 않는다(DEC-2026-10-31-37).

## 단계

| 단계 | 들어오는 것 | 남는 것 | 다음을 시작할 수 있을 때 | 역할 | 있는 곳 | 지금 |
|---|---|---|---|---|---|---|
| 아이디어 | 사용자의 말, 직관, 문제 | 아이디어 노트 한 장(다섯 속성, 조건, 확인된 무게) | 사용자가 고를 때 — 문턱이 없다. 아이디어는 어느 단계에서든 쓸 수 있다 | builder | 팩 `ideation`(`ideation.shape`, `kb ideas`) | 있음 |
| 기획 | 아이디어 노트, 또는 바깥의 기획 원천(Notion, 티켓) | 기획 묶음: 원문(`source/`), 근거(`audit/`: 사실 목록·대조표·결함·격리·영향), 정리본(PRD·Logical Tech Spec) — 주입되는 것은 정리본과 결정뿐 | `kb planning check` 가 행선지 없는 행·두 번 센 행·코드 표현을 보이지 않고, 새 컨텍스트 검사를 거쳤을 때 | builder | 코어 `strata.planning` | 있음 |
| 명세 | 기획 문서 | 바라는 명세: 목표, 범위, 증거가 붙은 검증 가능한 기준, 제약, 차이 목록 | 모든 기준이 증거를 가질 때 | builder | 코어 `strata.spec` | 있음 |
| 디자인 | 디자인할 것(문서·실물·이미지·포스트·화면)이 있는 명세나 의뢰 | 작업자의 디자인 브리프(목적·보는 사람·매체·제약·참조와 반응·인수 기준·산출물). 프로젝트·브랜드의 취향 노트와 관계식이 계산되는 기법에 기댄다 | 사람이 인수 기준을 판정하고 결과물을 `design_ref` 로 가리킬 때 — 제품으로 가면 그다음은 프론트엔드 디자인 계약(구현 흐름, 팩과 무관) | builder | 팩 `design`(`design.brief`, `design.taste`) | 있음(팩) |
| 오더 | 승인된 명세(와 계약) | 오더 하나와 레이어·작업자마다 태스크 파일 | 모든 태스크가 추측 없이 만들 수 있을 만큼 완전할 때 | builder | 코어 `strata.order` | 있음 |
| 구현 | 태스크 파일 하나 | 코드, 테스트, 증거 | 태스크의 레이어 안에서 테스트가 통과할 때 | worker | 코어 `strata.build-task` | 있음 |
| 검증 | 완료 주장 | 주장에 붙은 증거 | 증거가 새것이고 주장을 덮을 때 | 누구나 | 코어 `strata.verify` | 있음 |
| 리뷰 | 다시 볼 만한 결정이나 변경 | 리뷰어의 답과 그에 따라 한 것 | 답을 처리했을 때 | reviewer | 코어 `strata.review` | 있음 |
| 배포 | 검증된 변경 | 배포 전 노트(사실, 가정, 되돌리기)가 붙은 배포 | 로컬 실행으로 확인할 수 없는 것만 그 환경에서 확인할 때 | operator | 카드 `rec.deploy.only-for-env-specific-verification`, 역할 operator — 배포 절차는 프로젝트마다 달라 코어 스킬을 두지 않는다(DEC-2026-11-01-17) | 있음(카드와 역할) |
| 운영 | 돌아가는 시스템: strata 자체 측정, 그리고 제품 자신의 흐름(QA 장부, 커버리지 테스트 케이스)의 산출물 — 읽기만 | 시간에 따른 지표, 나빠진 지표마다 신호 노트 한 장과 사람이 고른 행선지 | 무엇을 고칠지(방법론 백로그 항목, 결정, 아이디어 노트, 기획 문서, 또는 버림)를 사람이 골랐고 받는 쪽이 있을 때 | librarian(매일 지표와 후보), builder(사람과 함께) | 코어 `strata.signal`, `kb indicators`(프로젝트 Tier P `indicators.yaml` 의 읽기 전용 명령), `kb signals`. kit 은 제품의 흐름에 쓰지 않고, 제품 장애·피드백은 제품의 일이다(DEC-2026-11-01-17) | 있음 |
| 회고 | 기간, 프로젝트, 결정 하나 | 사용자의 학습 노트와 넘길 후보 | 사용자가 자기 말로 설명했을 때 | builder | 코어 `strata.retro` | 있음 |

회고와 운영에서 흐름은 다시 아이디어와 백로그로 돌아온다.

## 단계 산출물의 연결

연결마다 문서의 필드 하나와 그것을 읽는 검사가 있다(DEC-2026-11-01-18). 새 단계의 검사는 집행 묶음 `stages` 로 돌고, 프로젝트가 올리지 않으면 알리기만 한다(`kb enforce run --family stages -- <검사>`).

| 어디서 → 어디로 | 연결 | 검사 |
|---|---|---|
| 아이디어 → 기획 | 묶음의 `source/` 가 출발한 아이디어 노트를 지닌다 | `kb planning check`(사실마다 행선지) |
| 기획 → 기존 일 | `audit/impact.md`: 기획의 주제 노드에 걸린 명세·코드·결정·다른 기획 | `kb planning impact` |
| 기획 ↔ 명세 | 명세의 `sources:` 가 기획을, 기획의 `implementation.spec` 이 명세를 가리킨다 | `kb divergence`(사람이 기획과 코드를 판정) |
| 명세 → 디자인 | 태스크의 `design_ref` 가 디자인 산출물을 가리킨다 | `kb design check` |
| 명세 → 태스크 | 태스크의 `scope.docs_to_update` 와 레지스트리에서 거른 제약 | strata.order 검증 |
| 명세 ↔ 코드 | `covers`(경로·심볼) | `kb coverage-gate` |
| 결정 ↔ 코드 | 결정의 `affects` | `kb coverage-gate` 재확인(알림) |
| 운영 → 다음 일 | 지표의 `nodes` 가 신호 노트에 붙고, 노트의 `routed_to` 가 사람이 고른 백로그 항목·결정·아이디어·기획을 가리킨다 | `kb signals check` |
| 회고 → 다음 일 | 학습 노트의 넘길 후보, 후보마다 간 곳 | strata.retro 검증 |

## 모든 단계에 걸치는 것

단계가 아니라, 어느 단계에서든 필요할 수 있는 것이다.

| 스킬 | 언제 |
|---|---|
| `strata.decision` | 앞으로의 일을 묶는 제약이 정해지거나 드러난 순간 |
| `strata.kb-update` | 지식 문서가 맡은 코드가 바뀌었을 때 |
| `strata.handoff` | 세션이나 작업이 끝날 때 |
| `strata.distill` | 판단이 이 프로젝트 밖에서도 통할 때 |
| `strata.translate` | 카드·스킬·문서에 다른 언어판이 필요할 때 |
| `using-strata`, `strata.init-wizard` | 세션에 들어올 때, 프로젝트를 설정할 때 |

## 단계가 있는 곳

- **코어** — 프로젝트와 관계없이 모든 세션에 필요한 것: 명세, 오더, 구현, 검증, 리뷰, 회고, 기획(DEC-2026-11-01-03), 그리고 운영 신호(DEC-2026-11-01-14).
- **팩** — 고른 사람만 쓰는 것. 사용자 층에 설치한다(`kb skills install`): 아이디에이션.
- **프로필 카드** — 프로젝트의 종류(프론트엔드, 백엔드)에 묶이는 것: 디자인 계약.
- **프로젝트 층** — 한 제품이나 도메인에 묶이는 것(그 화면, 장부, 결함 저장소).

## 단계 사이의 제안

코어 스킬마다 레지스트리 옆의 `skills/next.yaml` 에 `next:` 후보가 있다. 스킬, 이유, 그리고 선택적으로 영역과 그 영역이 제안만 할 때 쓸 문구다. 세션 시작의 라우팅이 이것을 읽지 않도록 레지스트리 밖에 둔다(DEC-2026-11-01-15). 팩이나 프로젝트 층은 경로 안에 `next:` 를 두어도 된다. `kb skills next <스킬>` 이 그 후보를 순서대로 보이고 "아무것도 안 함"을 끝에 두며, 어떤 경우에도 0 으로 끝난다. 사용자가 고른 것은 활성 파일과 핸드오프의 판단 과정 절에 적는다. 아키텍처 문제를 정한 경우에만 결정 기록이 된다.

## 빈 곳, 채울 순서

표의 단계 가운데 채울 차례를 기다리는 것은 없다. 기획이 기존 일에 미치는 영향 — 그 주제 노드의 명세·코드·결정·다른 기획 — 은 `kb planning impact` 가 묶음의 `audit/impact.md` 에 쓴다(DEC-2026-11-01-16).
