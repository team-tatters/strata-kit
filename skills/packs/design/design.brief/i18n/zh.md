# design.brief

## 概述

这是本人的设计阶段。无论设计的是什么——文档、实物、图片、帖子、界面——工作都从一份简报开始：它为了什么、谁会看、用什么媒介、受哪些约束、参考什么，以及什么成立时才算完成。简报属于本人；代理只负责提问和记录，不替人决定品味。设计依托于本人的品味以及表达它的技法（玻璃般的表面、浮起的柔和阴影、层叠的边框与明暗）；简报写明这项工作用到哪些。

前端设计契约（core/docs/<locale>/architecture/frontend-design-contract.md）是另一回事：它是把已定的设计带进代码的技术流程。本扩展包既不遵循它，也不修改它（DEC-2026-11-01-09）。两者只在一处交汇：当交付物进入产品时，契约用 `design_ref` 指向它。把本人的表达转换成产品的 token 是实现的工作。

## 适用场景

本人要设计某样东西，不论媒介；规格或发布需要设计某样东西；本人想对照目的来判定一个设计。不用于编写规格（strata.spec），也不用于实现界面（strata.build-task）。只是讨论设计时是只读；写简报时升为单会话（DEC-2026-11-01-18）。

## 流程

1. **简报。** 一次问一个问题，写出七个部分：Purpose、Audience、Medium and format、Constraints、References、Acceptance criteria、Deliverable（目的、受众、媒介与形式、约束、参考、验收标准、交付物）。目的先问要设计的是什么 — 网页、应用界面、幻灯片、报告、信息图、海报、图片或帖子、实物，或其他；并在简报的 frontmatter 中写成 `category`（`web`、`app`、`slides`、`report`、`infographic`、`poster`、`image`、`post`、`object`、`other`）。接着问这件作品必须传达的那一句话，再问内容的顺序 — 必须有的和可以舍去的。类别决定第 3 步用哪个适配器。没有答案的部分写“未知”。证据：简报及其类别。
2. **参考。** 对每个参考，询问本人最先注意到什么、其中是什么造成了这种感觉、它是否属于这项工作。把答案写在链接旁边。如果项目或品牌有品味笔记和表现笔记(design.taste)，写明这项工作依托的品味条目(#tag)和技法。本人按原文认可的反应或拒绝，经由 design.taste 作为来自这份简报的信号写入品味笔记。证据：References 部分。
3. **自己做或委托。** 由本人设计，或由代理在简报范围内起草。代理提出的选项要标明是代理的；由本人选择。在 `data/adapters.md` 中读取与简报类别对应的适配器：幻灯片、报告和信息图用文档适配器（论证、行动式标题、图表与结构的选择）；网页和应用在本人选了外部设计技能时用该技能，否则用该文件里简短的备用规则 — 二者不同时使用。交付物是网页或应用界面且本人愿意时，使用本人已经安装的设计技能 — 例如 Taste Skill（Leonxlnx/taste-skill，`design-taste-frontend`）或 Impeccable（pbakaus/impeccable）。先问用哪个，不要自己安装。把简报的目的、受众和约束，以及项目或品牌已有的原语和技法交给它（Taste Skill 用 `--keep palette,type`，Impeccable 用 `DESIGN.md`）。那个技能选的是代理一方的选项，不是本人的品味；决定的仍是简报的验收标准和本人的判定（DEC-2026-11-01-12）。证据：草稿、用到的技能（如有）和本人的选择。
4. **判定。** 把 `data/adapters.md` 中的通用检查作为代理的建议，提出来当作验收标准的候选；只有本人选中的才进入标准。每条验收标准由本人判定，并写下其结论。未通过的标准会把作品退回到造成问题的那一步 — 目的、内容顺序、层级、版式、数值或焦点 — 而不只是显现问题的那个地方。在 Deliverable 部分用 `design_ref`（`kind`、`ref`、`version`）指向结果。当结果进入产品时，产品自己的流程从这个 `design_ref` 接手。证据：判定和引用。
5. **下一步。** `python3 -m kb skills next design.brief`：产生了要记录的反应或拒绝时用 design.taste，交付物进入产品时用 strata.order，或 strata.review，或什么都不做。

## 借口与反驳

| 想法 | 反驳 |
|---|---|
| “只是一张海报，写简报太小题大做。” | 五行就够了。没有目的和受众，谁也说不清它是否完成。 |
| “我知道这里什么好看。” | 那是模型见过的东西的平均。品味是本人对其参考的反应；去问。 |
| “有参考链接就够了。” | 链接说不出什么才重要。写下本人对什么有反应。 |
| “产品的 token 规则应该决定这个。” | 这里不是。契约在 design_ref 处接收交付物；转换由实现来做。 |
| “Medium and format 部分已经说明这是什么了。” | 那一部分写的是尺寸和文件类型。要设计的是什么，决定适配器和外部技能；先问这个。 |
| “适配器有不错的默认值，直接套用。” | 它们是工艺检查和起点，不是本人的外观。本人的参考和品味优先。 |

## 警示信号

- 没有简报就交付的产物。
- 本人从未说过的目的、受众或验收标准。
- 只列出链接的参考。
- 把代理选择的外观记录为本人的品味。

## 验证

- 简报有用本人的话写成的七个部分和类别，未知之处已标明。
- 每条验收标准都有本人的判定。
- Deliverable 部分用 design_ref 指向结果。
